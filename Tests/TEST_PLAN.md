# Стратегия тестирования Loca Loca

**Статус:** проектирование, версия 1.0  
**Базовая версия кода:** `main` на коммите `c8116c5da0f1e9a7354830fb0e651bab02aedf58` (9 ноября 2026 г.).  
**Область:** Windows-клиент WinUI 3, ASP.NET Core API, PostgreSQL, HTML-карта, установщик.

## 1. Цель

Проверять не только успешный сценарий, но и границы входных данных, отказоустойчивость, изоляцию данных разных аккаунтов и корректность хранения фотографий. Критичные дефекты — потеря данных, доступ к чужим данным, обход авторизации, повреждение файлов и невозможность запуска клиента — должны обнаруживаться до публикации сборки.

Тесты не должны обращаться к рабочей базе Supabase, к личной базе пользователя или к облачному API, используемому реальными установками приложения.

## 2. Объект тестирования

Система состоит из четырёх основных частей:

1. **Desktop-клиент:** C# / WinUI 3, .NET 10, WebView2. Отвечает за интерфейс, авторизацию, вызовы API, локальные настройки и отображение карты.
2. **API:** ASP.NET Core Minimal API, .NET 10, Npgsql. Обрабатывает аккаунты, каталог, посещения, список желаний, личные точки карты и фотографии.
3. **База данных:** PostgreSQL. Хранит аккаунты, справочники, посещения, фотографии в `bytea`, wishlist и пользовательские точки.
4. **Поставка:** PowerShell-скрипты и Inno Setup. Сборка публикует Windows-приложение и локальный API, установщик создаёт и удаляет принадлежащие приложению локальные данные.

Основные API-маршруты находятся в `Server/LocaLoca.Api/Program.cs`. Структура базы — в `database/01_schema.sql`, начальные записи — в `database/02_seed.sql`, миграции — в `database/03_*.sql`–`database/07_*.sql`.

## 3. Уровни тестирования

| Уровень | Что проверяется | Где размещать |
|---|---|---|
| Unit | Чистая бизнес-логика, преобразования, валидация, формирование URI и DTO | `Tests/LocaLoca.Tests` |
| API integration | HTTP-контракт, авторизация, статусы ответов, взаимодействие с PostgreSQL | `Tests/LocaLoca.Api.Tests` |
| Database integration | Ограничения, внешние ключи, каскады, индексы, миграции и права роли | `Tests/LocaLoca.Database.Tests` |
| UI / system | Пользовательские сценарии WinUI 3 и WebView2 на Windows | ручной регресс; автоматизация отдельным этапом |
| Release smoke | Сборка, установка, обновление и удаление приложения | Windows CI + ручная проверка установщика |

### Unit-тесты

Целевой фреймворк — `net10.0`, xUnit и стандартные assertions. Не следует подключать тестовый проект напрямую к `LocaLoca/LocaLoca.csproj`: это WinUI-приложение с Windows-specific target framework и зависимостями App SDK. Такой reference сделает обычный unit-набор зависимым от Windows UI runtime.

Перед массовым написанием unit-тестов нужно выделить тестируемую логику в обычную библиотеку `LocaLoca.Core` с target framework `net10.0`. В неё имеет смысл переносить только независимые от XAML/Windows классы и функции. Не нужно создавать абстрактный слой ради покрытия строк.

### API integration-тесты

Основной инструмент — `Microsoft.AspNetCore.Mvc.Testing` / `WebApplicationFactory` и настоящий PostgreSQL из Testcontainers. Проверять маршруты через HTTP, а не вызывать обработчики напрямую: важны сериализация, middleware, заголовки, multipart-загрузка и реальные ограничения базы.

Для `WebApplicationFactory` точке входа API потребуется доступный тестовой сборке тип `Program` (обычно через `public partial class Program { }`). Подключение к БД и секрет сессий должны задаваться тестовой конфигурацией. Сейчас строка подключения считывается при старте приложения из переменных окружения; тестовый хост должен получать только строку временного контейнера.

### Database integration-тесты

Поднимать отдельную одноразовую PostgreSQL-базу. Для проверки API использовать отдельную роль с правами приложения, а не суперпользователя: иначе тесты не обнаружат ошибки в GRANT и readiness-проверке. Удалять контейнер после завершения набора тестов.

### UI и системные проверки

Пока нет выделенного UI automation framework и стабильных AutomationId для всех важных элементов. Первый этап — формализованный ручной регресс на Windows 10/11. После стабилизации интерфейса можно оценить FlaUI/UIA3 для нативных окон WinUI 3. Playwright не заменяет UI-тесты WinUI; его можно использовать отдельно для браузерной части карты, если появится изолируемый JS-контракт.

## 4. Приоритеты

- **P0 — блокирующие:** авторизация и изоляция аккаунтов; запись/удаление пользовательских данных; сохранение и чтение фотографий; корректное подключение к БД; запуск и удаление установленного приложения.
- **P1 — важные:** поиск и фильтрация каталога; посещения и wishlist; личные точки карты; смена имени; переключение темы и её сохранение.
- **P2 — дополнительные:** граничные визуальные состояния, длинные подписи, необычные имена файлов, повторные действия, производительность больших списков.

P0 должны проходить перед выпуском. P1 — перед слиянием функциональных изменений в `main`. P2 — в регрессионном наборе и при изменениях соответствующих областей.

## 5. Ключевые правила тестовых данных

- Для каждого прогона использовать собственную базу или уникальный набор записей.
- Создавать как минимум два аккаунта (`user A` и `user B`) для проверок доступа к чужим посещениям, точкам и фото.
- Логины тестовых аккаунтов формировать с уникальным суффиксом, например `it_<guid>`.
- Тестировать и пустую базу, и базу с данными из `database/02_seed.sql`.
- Даты для проверок «сегодня / будущее» вычислять относительно даты на тестовом сервере, а не фиксировать устаревающую календарную дату.
- Фотографии хранить как небольшие тестовые бинарные fixtures с корректными сигнатурами JPEG/PNG/WebP/GIF/BMP. Для лимитов размера генерировать поток в памяти, а не коммитить большие файлы.
- Не использовать реальные пароли, токены, адреса Supabase или данные пользователя в репозитории и CI.

## 6. Что должно проверяться сквозным образом

Критические пользовательские цепочки:

1. Регистрация → выход/повторный вход → загрузка каталога → создание посещения → получение списка посещений.
2. Создание посещения с фотографиями → чтение списка фото → получение бинарных данных → удаление фото/посещения.
3. Добавление достопримечательности в wishlist → отображение на карте → удаление из wishlist.
4. Создание личной точки со статусом planned → изменение на visited с датой и оценкой → отображение маркера → удаление точки.
5. Изменение display name → повторный запрос профиля/перезапуск клиента → новое имя отображается.
6. Переключение light/dark → проверка окна, диалогов и карты → перезапуск → выбранная тема восстановлена.
7. Установка → первый запуск и подключение к API → удаление → проверка очистки локальных данных без воздействия на облачную БД.

## 7. Известные ограничения тестируемости

1. В API обработчики, SQL и чтение конфигурации сосредоточены в одном top-level `Program.cs`. Это допустимо для текущего размера приложения, но усложняет unit-тестирование. На первом шаге достаточно добавить тестируемый entry point и тестовую конфигурацию; крупный рефакторинг до написания integration-тестов не требуется.
2. У API нет выделенного интерфейса подключения к БД: строка подключения считывается в переменную при старте. Изменение окружения между параллельными тестами небезопасно. До внедрения фабрики соединений тестовые API-наборы следует запускать последовательно в рамках одного fixture.
3. Клиент — WinUI 3 с target framework `net10.0-windows10.0.19041.0`. Его нельзя считать обычной кроссплатформенной библиотекой. UI-регресс должен выполняться на Windows.
4. Текущий `database/01_schema.sql` уже содержит столбцы `image_data` и `content_type`. Поэтому применение `07_migrate_photo_storage.sql` к новой схеме проверяет повторный запуск и права, но не полноценный upgrade старой инсталляции. Для upgrade-теста потребуется отдельный зафиксированный fixture старой схемы.
5. API возвращает общий 503 при ошибках Npgsql. Следует отдельно проверить, не маскирует ли этот middleware ошибки пользовательского ввода (например, ссылку на несуществующий attraction) как временную недоступность БД. Для таких случаев желательно явно зафиксировать ожидаемый контракт 4xx и при необходимости исправить обработчик.

## 8. Критерии готовности тестового контура

- Все три тестовых проекта добавлены в решение или доступны отдельными командами `dotnet test`.
- Unit-набор не требует Windows UI runtime.
- API integration-набор запускается на временной PostgreSQL и не обращается к Supabase.
- База тестов и роль приложения создаются автоматически; секреты берутся из временной конфигурации.
- Проверки изоляции выполняются для двух разных аккаунтов.
- Тестовые данные и временные файлы удаляются после прогона.
- CI публикует понятный результат `dotnet test`; падение P0 блокирует PR.
- Ручной Windows-регресс имеет воспроизводимые шаги и фактический результат, а не отметку «проверено» без протокола.

## 9. Порядок реализации

1. Подготовить test infrastructure: проекты, версии пакетов, временный PostgreSQL fixture и test-only конфигурацию API.
2. Реализовать DB smoke/constraints и API auth/readiness.
3. Добавить API-тесты посещений, wishlist, карты и фотографий.
4. Выделить первые чистые функции клиента в `LocaLoca.Core` и покрыть unit-тестами.
5. Добавить CI workflow для unit, API и DB наборов.
6. Ввести ручной release checklist для UI, WebView2 и установщика; позднее автоматизировать стабильные UI-сценарии.

Подробные идентификаторы сценариев находятся в [TEST_CASES.md](TEST_CASES.md), правила запуска и изоляции — в [TEST_ENVIRONMENT.md](TEST_ENVIRONMENT.md).


## 10. Реализация первого автоматизированного этапа

Создан отдельный проект `Tests/LocaLoca.Api.Tests` с `WebApplicationFactory<Program>` и xUnit. Первая версия проверяет HTTP-контракт, health/readiness, раннюю валидацию регистрации и обязательную авторизацию защищённых маршрутов.

Первый набор намеренно не поднимает PostgreSQL и не обращается к Supabase, Render или внешним сайтам. Для тестового хоста строка подключения задаётся безопасной заглушкой `CHANGE_ME`, отдельный временный каталог данных используется вместо пользовательского профиля, а тестовый секрет задаётся только в памяти тестового host.

Это не означает, что операции с данными уже полноценно протестированы: успешная регистрация, посещения, wishlist, фотографии, миграции, ownership двух аккаунтов и ограничения PostgreSQL требуют следующего этапа с одноразовой локальной PostgreSQL (Docker/Testcontainers). Такой контур не должен использовать рабочий Supabase.
