# План тестирования Loca Loca

## Цель

Обнаруживать регрессии до слияния в `main`, прежде всего:
1. утечки данных между аккаунтами;
2. потерю или повреждение посещений и фотографий;
3. неправильную проверку авторизации и паролей;
4. нарушения ограничений PostgreSQL и миграций;
5. поломки UI и установщика на Windows.

## Уровни

### 1. Unit tests — `Tests/LocaLoca.Tests`

Быстрые проверки чистой логики без БД и сетевых вызовов.

Текущая реализация:
- PBKDF2: случайная соль, корректная проверка, неверный пароль, повреждённая запись;
- HMAC-сессии: выпуск/проверка, изменённая подпись, повреждённый токен, недостаточный секрет;
- изображения: сигнатуры JPG/PNG/WEBP/GIF/BMP и соответствие MIME.

Дальше:
- валидация безопасных путей для локальных временных файлов;
- проверки обработки границ и пустых данных в общих DTO/валидаторах после их выделения в отдельные классы.

### 2. API integration tests — `Tests/LocaLoca.Api.Tests`

Тестируют ASP.NET Core через `WebApplicationFactory<Program>` и настоящий HTTP.

PostgreSQL берётся из одноразового Testcontainers-контейнера. Проверяются реальные запросы, SQL и ownership. Это основной контур для P0-безопасности.

Текущая реализация покрывает:
- `/health` и `/ready`;
- регистрацию, хранение PBKDF2-хеша и конфликт логина;
- вход с правильным и неправильным паролем;
- отказ без Bearer-токена;
- изоляцию посещений между двумя аккаунтами;
- изменение и удаление посещения владельцем;
- изоляцию wishlist;
- отказ в изменении и сокрытие чужой личной точки на карте;
- создание, изменение и удаление собственной точки;
- загрузку и чтение бинарной фотографии только владельцем;
- отказ в удалении чужой фотографии и удаление фотографии владельцем;
- отклонение неправильного содержимого фото до записи.

Следующие приоритетные API-сценарии:
- update/delete посещений владельцем и попытка обращения по несуществующему ID;
- CRUD личных точек и переход planned/visited;
- массовая загрузка фотографий, лимит количества/размера, недопустимые расширения;
- удаление фото и каскадная очистка;
- некорректные/просроченные токены и подмена user ID;
- ошибки БД без раскрытия connection string или SQL-параметров клиенту.

### 3. Database tests — `Tests/LocaLoca.Database.Tests`

Тестируют PostgreSQL-объекты напрямую в отдельном контейнере:
- состав таблиц и типы фото-колонок;
- constraints рейтинга/координат;
- повторные посещения одной достопримечательности;
- уникальность пары wishlist;
- FK и каскады при удалении пользователя;
- повторное выполнение миграций 03/04/06/07;
- набор минимальных разрешений runtime-роли.

Следующий приоритет:
- проверка исторической схемы перед миграциями, а не только повторного запуска на актуальной схеме;
- тесты ограничения размера бинарного фото и допустимых content type;
- тесты поведения при отсутствии runtime-прав.

### 4. Windows regression

Выполняется на Windows runner или вручную на тестовом ПК:
- установка поверх предыдущей версии;
- чистая установка и запуск;
- регистрация/вход/выход;
- обе темы, профиль и поддержка;
- карта, выбор оценки у краёв viewport, посещения и фото;
- деинсталляция и подтверждение удаления только локальных данных;
- облачные записи должны оставаться в базе.

Для автоматизации UI можно позднее выделить WinUI-only проект на FlaUI. Это не блокирует API и DB CI.

## Приоритеты

- **P0:** авторизация, ownership, изоляция пользователей, сохранность фото, DB constraints/cascade, безопасная конфигурация.
- **P1:** бизнес-операции каталога, wishlist, профиля, карта, UI, installer upgrade.
- **P2:** визуальные мелочи, производительность больших списков/изображений, edge cases редких сценариев.

## Правило готовности PR

Изменение считается проверенным только после:
- успешной сборки затронутых проектов;
- прохождения применимых unit/API/database jobs;
- анализа CodeQL;
- secret scan;
- Windows installer build для изменений клиента/установщика;
- ручной проверки UI, когда меняются визуальные сценарии.

Нельзя считать тест покрытым, если он только описан в Markdown: должен существовать исполняемый тест, который завершился успешно.
