# План тестирования Loca Loca

## Назначение

План определяет уровни тестирования, приоритеты проверок и критерии, по которым изменение можно считать проверенным перед слиянием в `main`.

Основной фокус — безопасность аккаунтов и данных, целостность PostgreSQL, корректность API и отсутствие регрессий в Windows-клиенте и установщике.

## Ключевые риски

В первую очередь тестирование должно обнаруживать:

1. Доступ пользователя к чужим данным или действия от имени другого пользователя.
2. Потерю, повреждение или некорректную выдачу посещений и фотографий.
3. Ошибки аутентификации, проверки паролей и проверки Bearer-сессий.
4. Нарушение ограничений PostgreSQL, внешних ключей, каскадов и миграций.
5. Сбои клиентского интерфейса, настройки облачного API, установки и удаления приложения.
6. Случайное попадание секретов или production-конфигурации в репозиторий и CI.

## Уровни тестирования

### 1. Unit-тесты — `Tests/LocaLoca.Tests`

Проверяют изолированную логику без БД и сетевых вызовов.

**Уже реализовано:**
- PBKDF2: случайная соль, корректная проверка, неверный пароль и повреждённая запись;
- HMAC-сессии: выпуск и проверка, изменённая подпись, повреждённый токен и недостаточный секрет;
- изображения: сигнатуры JPG/PNG/WEBP/GIF/BMP и соответствие MIME.

**Следующие задачи:**
- безопасная валидация путей для локальных временных файлов;
- обработка граничных и пустых данных в общих DTO/валидаторах после их выделения в отдельные классы.

### 2. API integration tests — `Tests/LocaLoca.Api.Tests`

Проверяют ASP.NET Core через `WebApplicationFactory<Program>`, настоящий HTTP и отдельную PostgreSQL из Testcontainers. Это основной контур проверки авторизации и ownership.

**Текущее покрытие:**
- `/health` и `/ready`;
- регистрация, PBKDF2-хеш пароля и конфликт логина;
- вход с корректным и неправильным паролем;
- истёкшие, повреждённые и подменённые Bearer-токены через HTTP;
- отзыв текущей сессии через logout и повторный отказ в доступе;
- ограничение частоты массовых попыток входа и регистрации;
- отказ в доступе без Bearer-токена;
- изоляция посещений двух аккаунтов;
- изменение и удаление посещения владельцем;
- изоляция wishlist;
- отказ в изменении чужой личной точки и сокрытие её от другого пользователя;
- создание, изменение и удаление собственной точки;
- загрузка и чтение бинарной фотографии владельцем;
- отказ в чтении и удалении чужой фотографии;
- отклонение некорректного содержимого фото до записи.
- отрицательные update/delete для несуществующих ID посещений и личных точек;
- запрет изменения и удаления чужой личной точки, сохранение исходной записи после невалидного update;
- отказ в загрузке фото к чужим или несуществующим посещениям/точкам;
- 404 для чтения/удаления несуществующих фото и повторного удаления;
- границы загрузки: ровно 20 МиБ, превышение на 1 байт, ровно 10 файлов, 11 файлов и превышение суммарного лимита;
- отсутствие частичных записей при отклонении загрузки;
- безопасная обработка ошибок ограничений PostgreSQL через HTTP API: FK/CHECK/NOT NULL → 400, UNIQUE → 409, без раскрытия деталей БД.
- 12 параллельных обновлений одного посещения: каждый запрос завершается успешно, итоговая запись содержит согласованный набор полей одного обновления;
- 12 одновременных добавлений одинакового элемента в wishlist: повторяющиеся запросы не создают дубликатов;
- остановка PostgreSQL: liveness остаётся доступной, API возвращает безопасный HTTP 503, после перезапуска БД API восстанавливает доступ к ранее сохранённым данным.

**Граница текущей проверки конкурентности:** параллельные обновления посещения работают по принципу last-write-wins. Тест подтверждает целостность итоговой строки, но не обнаружение устаревшей версии и не возврат HTTP 409 при конфликте редактирования. Для optimistic concurrency потребуется отдельный механизм версии записи и отдельный пользовательский контракт.

**Следующие приоритетные проверки:**
- обращения к несуществующим ID для update/delete;
- полный CRUD личных точек и переходы planned/visited;
- массовая загрузка фотографий и лимиты количества/размера;
- недопустимые расширения и MIME;
- удаление фото и каскадная очистка;
- сохранение отзыва сессий в PostgreSQL, чтобы logout оставался действительным после перезапуска облачного API;
- защита от распределённого перебора с нескольких IP и согласование лимитов с доверенной proxy-конфигурацией;
- ошибки БД без раскрытия connection string, паролей и SQL-параметров клиенту.

**Ограничение текущей реализации:** список отозванных токенов хранится в памяти процесса. Logout немедленно отзывает токен для работающего экземпляра API, но после перезапуска облачного API при сохранённом `LOCA_SESSION_SECRET` такой токен может снова пройти HMAC-проверку до истечения срока. Для долговременного отзыва требуется хранение denylist в PostgreSQL. Счётчики rate limit также находятся в памяти отдельного процесса и сбрасываются при его перезапуске; для нескольких API-инстансов понадобится общий распределённый limiter. До настройки доверенной обработки proxy-заголовков IP-лимиты следует проверять на реальной облачной топологии.

### 3. Database tests — `Tests/LocaLoca.Database.Tests`

Проверяют PostgreSQL-объекты непосредственно на отдельном контейнере.

**Текущее покрытие:**
- состав таблиц и типы фото-колонок;
- constraints рейтинга и координат;
- повторные посещения одной достопримечательности;
- уникальность пары wishlist;
- внешние ключи и каскады при удалении пользователя;
- повторное выполнение миграций 03/04/06/07;
- минимальный набор разрешений runtime-роли.

**Следующие приоритетные проверки:**
- обновление действительно исторической схемы, а не только повторный запуск миграций на актуальной;
- ограничение размера бинарного фото и допустимые content type;
- поведение при отсутствии отдельных runtime-разрешений.

### 4. Windows regression

Выполняется на Windows runner или вручную на отдельном тестовом компьютере. Этот уровень нужен для проверки реального пользовательского сценария и не заменяется API-тестами.

Проверки включают:

- чистую установку и запуск;
- установку поверх предыдущей версии;
- регистрацию, вход и выход;
- обе темы интерфейса, профиль и поддержку;
- отображение карты и выбор оценки у краёв viewport;
- посещения, wishlist, личные точки и фотографии;
- деинсталляцию и удаление только локальных данных;
- сохранность облачных записей после удаления клиента.

Автоматизацию UI можно позднее выделить в отдельный Windows-only проект, например на FlaUI. Это не блокирует выполнение API- и Database-тестов в текущем CI.

## Приоритеты

| Приоритет | Что проверять | Почему |
| --- | --- | --- |
| P0 | Аутентификация, ownership, изоляция пользователей, сохранность фото, DB constraints/cascade, безопасная конфигурация | Ошибки могут привести к раскрытию или потере данных |
| P1 | Каталог, wishlist, профиль, карта, UI, установка и обновление | Основные пользовательские операции и регрессии |
| P2 | Визуальные детали, производительность больших списков и изображений, редкие граничные сценарии | Улучшение качества и устойчивости |

## Критерии готовности Pull Request

Изменение считается проверенным только после выполнения применимых пунктов:

- успешно собраны затронутые проекты;
- пройдены применимые unit-, API- и database jobs;
- пройден CodeQL для соответствующих изменений;
- выполнен secret scan;
- для изменений клиента или установщика выполнена Windows-сборка;
- для визуальных и установочных сценариев выполнена соответствующая ручная regression-проверка.

Не отмечайте сценарий как покрытый только потому, что он описан в этом документе или в [TEST_CASES.md](TEST_CASES.md). Для статуса «Автоматизирован» должен существовать исполняемый тест; успешный результат подтверждается запуском теста.

## Изменение тестового плана

При добавлении функции или исправлении ошибки:

1. Определите, какие уровни тестирования затронуты.
2. Добавьте новый сценарий в [TEST_CASES.md](TEST_CASES.md), если он важен для повторной проверки.
3. Реализуйте исполняемый тест там, где это возможно.
4. Обновите статус сценария только после появления теста.
5. Для ручной проверки укажите условия запуска и ожидаемый результат.
