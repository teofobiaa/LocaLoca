# Друзья и совместные посещения

**Статус:** проектирование MVP.  
**Целевая база:** существующая PostgreSQL Loca Loca.  
**Внешние зависимости:** не требуются.

## 1. Цель

Пользователь должен иметь возможность:

1. Найти другого пользователя Loca Loca по точному логину.
2. Отправить запрос на добавление в друзья.
3. Принять или отклонить входящий запрос.
4. Удалить друга из списка.
5. При создании или редактировании собственного посещения пригласить одного или нескольких друзей отметить, что они были там вместе.
6. Увидеть подтверждённые совместные посещения в отдельном списке и на карте.

Это не должно превращать личный дневник в публичную ленту. Данные одного аккаунта не становятся автоматически доступными всем его друзьям.

## 2. Принципы приватности и безопасности

- Идентификатором для поиска служит точный `login`, а не `display_name`: отображаемые имена не уникальны.
- Список друзей виден только владельцу аккаунта.
- Запрос дружбы требует явного ответа получателя.
- Отметка о совместном посещении требует отдельного приглашения и согласия каждого участника.
- Нельзя добавлять другого пользователя в совместное посещение только по переданному с клиента `user_id`: сервер проверяет существующую принятую дружбу.
- Все операции используют владельца сессии, полученного из Bearer-токена. Переданный клиентом `owner_user_id` или `created_by_user_id` не считается доверенным.
- Совместное событие раскрывает приглашённому только явно выбранные поля: название места, координаты, дату и участников. Личные заметки, впечатления, исходные фотографии и остальные записи владельца не копируются и не открываются.
- Принятие приглашения не создаёт фиктивное посещение в личном дневнике другого участника. Оно добавляет событие в отдельный список «Вместе».
- Удаление друга запрещает новые приглашения между аккаунтами. Существующие подтверждённые события сохраняются как совместная история, пока один из участников не покинет событие или оно не будет удалено по правилам продукта.
- Нужны защита от самодобавления, повторных запросов, перебора логинов и массовой рассылки приглашений.

## 3. Предлагаемая модель данных

### 3.1. `friendships`

Одна строка на пару аккаунтов:

| Поле | Назначение |
|---|---|
| `user_low_id` | Меньший из двух user_id |
| `user_high_id` | Больший из двух user_id |
| `requested_by_user_id` | Кто отправил запрос |
| `status` | `pending`, `accepted`, `declined` или `blocked` |
| `created_at` | Время первого запроса |
| `updated_at` | Последнее изменение |
| `responded_at` | Время ответа, если он был |

Предлагаемые ограничения:
- композитный первичный ключ `(user_low_id, user_high_id)`;
- `user_low_id < user_high_id` и оба ID различаются;
- `requested_by_user_id` принадлежит этой паре;
- оба user_id имеют FK на `users(user_id) ON DELETE CASCADE`;
- повторный запрос для уже существующей пары обновляет/возвращает текущее состояние, но не создаёт дубликат.

Одна запись на пару позволяет не создавать две встречные дружбы. При `pending` получатель — второй участник, не совпадающий с `requested_by_user_id`.

### 3.2. `shared_visits`

Общая запись о событии, которое создал инициатор на основе собственного посещения или личной точки:

| Поле | Назначение |
|---|---|
| `shared_visit_id` | Идентификатор события |
| `created_by_user_id` | Автор события |
| `attraction_id` | Необязательная ссылка на место из каталога |
| `source_visit_id` | Необязательная ссылка на посещение автора |
| `source_map_place_id` | Необязательная ссылка на личную точку автора |
| `place_name` | Снимок названия, которое будет видно участникам |
| `latitude`, `longitude` | Координаты события |
| `visit_date` | Дата совместного посещения |
| `created_at` | Время создания |

Для первого MVP допустимы два источника: существующее посещение автора из каталога либо его личная точка карты. Если источник удалён, минимальные данные события остаются благодаря snapshot-полям. Проверка, что `source_visit_id` или `source_map_place_id` действительно принадлежит автору, должна выполняться в API в той же транзакции, что и создание события.

Событие не содержит полей `notes`, `impressions`, `image_data` или ссылок на фото. Это исключает непреднамеренное раскрытие личного содержимого дневника.

### 3.3. `shared_visit_participants`

Участники и ответы на приглашения:

| Поле | Назначение |
|---|---|
| `shared_visit_id` | Совместное событие |
| `user_id` | Приглашённый участник |
| `invited_by_user_id` | Кто отправил приглашение |
| `status` | `pending`, `accepted`, `declined` или `left` |
| `created_at` | Время приглашения |
| `responded_at` | Время ответа |

Первичный ключ — `(shared_visit_id, user_id)`. Автор создаётся как участник со статусом `accepted`. Для приглашённых пользователей сервер проверяет активную дружбу с автором и не позволяет приглашать самого себя.

### 3.4. Ограничения схемы

- Внешние ключи и каскады не должны оставлять записи участников без общего события.
- Нельзя иметь дублирующегося участника одного события.
- Статусы задаются CHECK constraints.
- Дата посещения не должна быть позже текущей даты по правилам API.
- Широта/долгота должны оставаться в диапазонах `-90..90` и `-180..180`.
- Изменение схемы выполняется новой миграцией, без переписывания уже применённых SQL-миграций.

## 4. Предлагаемый API-контракт

Все маршруты ниже — проектируемые, они ещё не реализованы.

### Друзья

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/me/friends` | Принятые друзья текущего пользователя |
| `GET` | `/api/me/friend-requests` | Входящие и исходящие запросы |
| `POST` | `/api/me/friend-requests` | Отправить запрос по точному логину |
| `POST` | `/api/me/friend-requests/{userId}/accept` | Принять входящий запрос |
| `POST` | `/api/me/friend-requests/{userId}/decline` | Отклонить входящий запрос |
| `DELETE` | `/api/me/friends/{userId}` | Удалить друга или отменить исходящий запрос |

Поиск по логину не должен раскрывать лишние сведения об аккаунте: достаточно минимальной карточки для подтверждения правильного человека (display name и точное совпадение логина).

### Совместные посещения

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/me/shared-visits` | События текущего пользователя и подтверждённые приглашения |
| `GET` | `/api/me/shared-visit-invitations` | Приглашения, ожидающие ответа |
| `POST` | `/api/me/shared-visits` | Создать событие и пригласить друзей |
| `POST` | `/api/me/shared-visits/{id}/accept` | Подтвердить участие |
| `POST` | `/api/me/shared-visits/{id}/decline` | Отклонить участие |
| `POST` | `/api/me/shared-visits/{id}/leave` | Покинуть событие |
| `DELETE` | `/api/me/shared-visits/{id}` | Удалить событие автором |

API должен получать создателя события из сессии, не доверяя полю автора в JSON. Для маршрутов accept/decline/leave проверяется, что текущий пользователь действительно является приглашённым участником.

## 5. Изменения интерфейса

### Страница «Друзья»

- поиск пользователя по логину;
- входящие запросы с кнопками «Принять» и «Отклонить»;
- исходящие запросы со статусом ожидания;
- список принятых друзей;
- действие «Удалить из друзей».

### Совместное посещение

В форме нового/существующего посещения появляется отдельный блок «С кем был»:
- выбор только из принятых друзей;
- отправка приглашений после сохранения записи;
- явный статус каждого приглашения;
- отсутствие возможности пометить друга подтверждённым участником без его согласия.

### Карта и список «Вместе»

Подтверждённые совместные события получают отдельный вид маркера и собственный фильтр. На маркере отображаются место, дата и список подтвердивших участие друзей. Личные фото, заметки и впечатления не показываются.

## 6. Последовательность реализации

1. Создать миграцию для `friendships`, `shared_visits` и `shared_visit_participants`.
2. Обновить runtime-права роли приложения и readiness-проверку.
3. Реализовать API запросов дружбы и серверную проверку ownership.
4. Реализовать создание совместного события, приглашение, принятие, отказ и выход.
5. Добавить страницу друзей и блок участников в форме посещения.
6. Добавить совместные события в отдельный раздел и слой карты.
7. Подключить автоматизированные тесты, включая проверки доступа двух пользователей.

## 7. Обязательные тесты

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| FRIEND-001 | Пользователь отправляет запрос самому себе | HTTP 400; строки нет |
| FRIEND-002 | Два пользователя одновременно отправляют запросы друг другу | Одна запись дружбы; нет дублирующихся отношений |
| FRIEND-003 | Посторонний пользователь пытается принять не адресованный ему запрос | HTTP 404/403; состояние не меняется |
| FRIEND-004 | Пользователь отправляет повторный запрос уже существующему другу | Нет дублирующей записи |
| SHARED-001 | Создатель приглашает пользователя, который не является его другом | HTTP 400/403; приглашение не создаётся |
| SHARED-002 | Приглашённый принимает корректное приглашение | Участник получает статус accepted и видит совместное событие |
| SHARED-003 | Неприглашённый пользователь пытается принять событие | HTTP 404/403 |
| SHARED-004 | Один участник запрашивает чужие личные заметки/фотографии через shared API | Приватные поля не возвращаются |
| SHARED-005 | Пользователь удаляет друга | Новые приглашения блокируются; старые события обрабатываются по установленным правилам |
| SHARED-006 | Автор пытается указать чужой `source_visit_id` или `source_map_place_id` | HTTP 404/403; событие не создаётся |
| SHARED-007 | Приглашённый пользователь покидает событие | Он больше не видит его среди активных совместных событий |
| SHARED-008 | Удаляется источник личного посещения после создания shared snapshot | Совместное событие остаётся целостным и не открывает исходные личные данные |

Проверки должны запускаться на отдельной PostgreSQL через локальный контейнер/Testcontainers. Рабочую Supabase использовать нельзя.

## 8. Безопасность и ограничения MVP

- Никакой регистрации через социальные сети и OAuth на первом этапе.
- Никакого автоматического импорта друзей из телефонной книги.
- Никакого доступа друга ко всей карте, списку посещений или альбому другого пользователя.
- Никакой передачи DB connection string или service-role ключа в клиент.
- Все изменения БД — SQL migration, применяемая администратором; приложение не выполняет DDL на старте.
- Время, участники и данные события валидируются сервером и ограничениями БД.

**Критерий готовности MVP:** два аккаунта могут стать друзьями, один отправляет приглашение к совместному посещению, второй подтверждает его, и событие появляется у обоих без раскрытия частных заметок и фотографий.
