# Единый центр уведомлений Loca Loca

**Статус:** проектная спецификация. Документ не означает, что API, миграции, фоновый обработчик или интерфейс уже реализованы.

## 1. Цель и границы

Все сохраняемые пользовательские уведомления должны поступать в единый центр приложения. Разделы профиля, карты, друзей, статистики и настроек не создают собственные независимые списки уведомлений и не реализуют собственные счётчики непрочитанного.

Центр уведомлений отвечает за:
- хранение уведомлений конкретного получателя;
- единый список, сортировку, пагинацию и состояние прочтения;
- единые настройки категорий и каналов доставки;
- маршрутизацию пользователя к исходному объекту или действию;
- дедупликацию и применение правил приватности;
- выдачу общего количества непрочитанных уведомлений.

В первую версию входит **только внутренняя доставка в приложении**. Email, web push и отдельные системные уведомления Windows не считаются реализованными каналами. Их можно добавить позже через тот же контракт доставки, не создавая новый центр.

Кратковременные сообщения об ошибке, успешном сохранении или валидации остаются обычной обратной связью текущего экрана. Они не должны засорять постоянный центр. Уведомление создаётся, когда пользователю нужно вернуться к событию или выполнить действие позднее.

## 2. Контекст текущей архитектуры

Текущий сервер — ASP.NET Core Minimal API; клиент — Windows/WinUI; постоянные данные находятся в PostgreSQL. API использует серверные сессии и получает идентификатор авторизованного пользователя из проверенной сессии. Новые маршруты центра должны следовать этой модели и не принимать recipient/user ID от клиента.

Социальная функция разрабатывается в открытом PR #132 (`feature/friend-user-search`); в этой ветке актуальная схема — v22. Она уже содержит `user_friendships`, `user_blocks` и `users.date_of_birth` с настройкой `date_of_birth_visibility` (`private`/`friends`/`registered`). Полная дата рождения доступна только владельцу, а профиль другим пользователям раскрывает максимум день и месяц. При реализации уведомлений сверяйся с текущим `database/migrations/manifest.json` и добавляй следующую свободную миграцию; не редактируй уже опубликованные SQL-файлы.

В текущей архитектуре не обнаружен общий inbox или отдельный надёжный фоновый обработчик. Следовательно, проектирование включает не только экран, но и постоянное хранилище с серверной маршрутизацией событий.

## 3. Модель уведомления

Уведомление — это запись для одного получателя, а не общий объект, доступный всем пользователям.

Предлагаемая модель `user_notifications`:

| Поле | Назначение |
| --- | --- |
| `notification_id` | Уникальный монотонный идентификатор |
| `recipient_user_id` | Получатель; внешний ключ на `users`, удаление аккаунта удаляет его inbox |
| `notification_type` | Стабильный код события, например `social.friend_request_received` |
| `actor_user_id` | Инициатор события, nullable; при удалении аккаунта становится NULL |
| `subject_type`, `subject_id` | Тип и идентификатор исходного объекта, если он есть |
| `payload` | Ограниченные структурированные данные для отображения; только allowlist-поля |
| `created_at` | Время создания в UTC |
| `read_at` | NULL, пока уведомление не прочитано |
| `dismissed_at` | Мягкое скрытие из списка, без немедленного физического удаления |
| `expires_at` | Необязательный срок актуальности для временных событий |
| `deduplication_key` | Ключ идемпотентности в пределах получателя |

Обязательные ограничения и индексы:
- уникальность `(recipient_user_id, deduplication_key)`, чтобы повторная доставка одного события не создавала несколько карточек;
- индекс ленты `(recipient_user_id, created_at DESC, notification_id DESC)`;
- частичный индекс непрочитанных записей по получателю;
- внешние ключи с явным поведением при удалении пользователя;
- CHECK/валидация допустимых значений типа на уровне приложения и тестов.

`payload` не должен становиться обходным способом передачи секретов или копии всего профиля. Не хранить bearer-токены, полную дату рождения без необходимости, пароли, приватные заметки поездок или произвольные HTML/URL. Идентификатор объекта недостаточен для доступа: при открытии целевого экрана сервер повторно проверяет права.

## 4. Единый путь создания событий

Все источники используют один серверный контракт — условный `INotificationService`/`NotificationService`:

- создание одного или нескольких уведомлений адресатам;
- получение списка и счётчика непрочитанного;
- отметка одного уведомления прочитанным;
- отметка всех уведомлений прочитанными;
- скрытие уведомления;
- чтение и изменение настроек.

Доменные endpoint'ы не формируют собственные таблицы, локальные счётчики или отдельные постоянные механизмы оповещения. Они сообщают сервису о факте доменного события и его безопасных параметрах. Формат карточки, дедупликация, правила доставки и состояние прочтения централизованы.

### Надёжная доставка

Для событий, возникающих одновременно с изменением данных (например, отправка/принятие заявки в друзья), запись исходного изменения и запись события в `notification_outbox` должны выполняться в одной транзакции PostgreSQL. Это исключает ситуацию, когда действие сохранилось, а событие потерялось из-за сбоя между двумя операциями.

Предлагаемая outbox-запись содержит `outbox_id`, `event_type`, `deduplication_key`, безопасный `payload`, `created_at`, `available_at`, `processed_at`, `attempt_count` и диагностический код последней ошибки без секретных данных. Обработчик забирает строки конкурентно через транзакционную блокировку (например, `FOR UPDATE SKIP LOCKED`), создаёт записи inbox и отмечает событие обработанным. Повторная обработка должна быть безопасной.

Outbox не является вторым центром уведомлений: это внутренняя очередь надёжной обработки. Пользователь читает только `user_notifications`.

Для первого этапа допустимо реализовать обработчик как отдельный hosted worker рядом с API либо как отдельный worker-процесс. Нельзя полагаться на таймер внутри одного экземпляра API без блокировки и идемпотентности: приложение может перезапускаться или работать в нескольких экземплярах.

## 5. Категории и типы событий

Тип события отделён от категории настроек. Это позволяет добавлять новые события, не менять UI-контракт для каждого раздела.

| Категория | Типы первой/следующей очереди | Условие |
| --- | --- | --- |
| Социальные события | `social.friend_request_received`, `social.friend_request_accepted` | Только после внедрения модели дружбы; блокировка имеет приоритет |
| Дни рождения | `birthday.reminder` | Только согласно настройке видимости даты, дружбе и настройкам получателя |
| Путешествия | Будущие напоминания о целях/запланированных поездках | Не включать, пока для события не определены источник, время и пользовательский сценарий |
| Системные | Важные события аккаунта и безопасности | Только события, для которых действительно требуется постоянная запись в inbox |

Не следует автоматически превращать каждое действие пользователя в уведомление. Например, изменение заметки или обычное обновление статистики не должно порождать запись без определённой пользовательской ценности.

## 6. Приватность и социальные правила

Правила доступа применяются на сервере при создании и выдаче уведомления. Скрытие карточки на клиенте не является контролем доступа.

### Дни рождения

Текущая приватность профиля уже использует `date_of_birth_visibility` со значениями:
- `private` — день рождения видит только владелец;
- `friends` — подтверждённые друзья;
- `registered` — любой авторизованный пользователь.

Публичная модель профиля возвращает только день и месяц; год и полная дата не раскрываются ни при одном значении. Будущий producer уведомлений должен использовать личное серверное значение даты рождения напрямую, заново проверять подтверждённую дружбу и блокировки и передавать клиенту только минимальные данные напоминания. Не добавляй новые значения в `date_of_birth_visibility` ради настройки напоминаний: предпочтение уведомлений — отдельная настройка получателя.

Напоминание адресуется только взаимно подтверждённым друзьям, а не всем зарегистрированным аккаунтам. Уведомление также зависит от настройки получателя для категории «Дни рождения». Точный момент отправки должен учитывать часовой пояс аккаунта; до появления сохраняемого IANA time zone нельзя использовать часовой пояс сервера как пользовательский.

### Блокировки и изменение отношений

Если одна сторона блокирует другую:
- новые социальные и birthday-уведомления между этой парой не создаются;
- уже созданные чувствительные уведомления пары не должны продолжать раскрывать профильные сведения;
- блокировка не порождает уведомление «вас заблокировали»;
- повторная проверка отношения/блокировки выполняется при выдаче чувствительного уведомления или его данных.

При удалении/отзыве дружбы будущие напоминания о днях рождения прекращаются. Старые уведомления не должны обходить новую настройку приватности.

### Изоляция аккаунтов

Получатель всегда вычисляется из авторизованной сессии. Любые операции чтения, отметки прочитанным и скрытия используют одновременно `notification_id` и серверный `recipient_user_id`. Нельзя позволять клиенту менять владельца уведомления, читать чужой счётчик или запрашивать inbox другого пользователя.

## 7. Настройки уведомлений

Настройки доставки отделены от настроек отображения блоков/стран/элементов интерфейса и от параметров сбора аналитики. Отключение отображения отдельного раздела не должно удалять уведомления или менять сбор аналитики.

Предлагаемая модель `user_notification_preferences`:
- `user_id`;
- `category_key` или `notification_type`;
- `channel`;
- `enabled`;
- `updated_at`.

В первой версии поддерживается канал `in_app`. Значение по умолчанию для категорий должно быть задано явно в спецификации продукта; отсутствие строки предпочтения не должно трактоваться по-разному в разных endpoint'ах. Будущие каналы могут добавляться без создания второго inbox.

## 8. API-контракт

Все маршруты требуют действующую сессию и работают только с уведомлениями текущего пользователя.

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/me/notifications?take=20&cursor=...` | Лента с keyset-пагинацией; фильтр `all/unread` допустим |
| `GET /api/me/notifications/unread-count` | Общий счётчик непрочитанных |
| `POST /api/me/notifications/{id}/read` | Прочитать одну запись |
| `POST /api/me/notifications/read-all` | Прочитать все записи текущего пользователя |
| `DELETE /api/me/notifications/{id}` | Скрыть одну запись (soft dismiss) |
| `GET /api/me/notification-preferences` | Получить настройки |
| `PUT /api/me/notification-preferences` | Сохранить валидированный набор настроек |

Для списка использовать стабильный курсор по паре `(created_at, notification_id)`, а не растущий OFFSET. Размер страницы ограничить (предлагаемый диапазон 1–50). Ответ содержит тип, безопасные поля, время создания, состояние прочтения и типизированную цель перехода; не содержит произвольный URL, который клиент должен открыть без проверки.

Ошибки и пустые результаты следуют общему JSON-контракту API. Повторная отметка уже прочитанного/скрытого уведомления идемпотентна.

## 9. Поведение интерфейса

Единый элемент доступа к центру размещается в общей области навигации приложения и виден независимо от открытого раздела:
- индикатор непрочитанного числа (при большом значении показывать ограниченный формат, например 99+);
- единая лента, сортировка от новых к старым;
- состояния «все» и «непрочитанные»;
- действие «прочитать» и «прочитать всё»;
- скрытие устаревшего/неактуального уведомления;
- переход к исходному объекту или действию после повторной проверки прав;
- корректное пустое состояние и состояние ошибки загрузки.

Разделы приложения могут инициировать доменные события, но не должны иметь собственные независимые бейджи/ленты для тех же постоянных уведомлений. Локальные подтверждения операций остаются transient feedback, а не дубликатами inbox-карточек.

На первом этапе центр должен работать при открытии приложения и при обновлении данных клиентом. Интервал фонового опроса и поведение при нескольких открытых окнах нужно выбрать после проверки сетевой нагрузки; не делать запрос к БД на каждый визуальный rerender. Счётчик можно обновлять вместе с загрузкой ленты и после действий пользователя.

## 10. Фоновая обработка дней рождения

Дни рождения — периодическое событие и требуют отдельного расписания. Обработчик должен:
1. выбирать только пользователей с режимом, допускающим напоминание;
2. вычислять локальный календарный день по часовому поясу получателя;
3. выбирать только взаимно подтверждённых друзей без блокировки в любом направлении;
4. учитывать настройки получателя;
5. создавать не более одного напоминания для пары «получатель — именинник — год»;
6. повторно проверять актуальные отношения и видимость перед выдачей;
7. быть безопасным при повторном запуске, перезапуске и параллельной работе нескольких экземпляров.

Не запускать эту обработку в каждом API-запросе и не рассчитывать на локальные часы Render/Windows. Поле даты рождения и режим видимости уже существуют; внедрение birthday producer зависит от сохранённого IANA-часового пояса, настроек уведомлений получателя и фонового расписания.

## 11. План реализации

**Этап A — ядро центра**
- уточнить окончательную версию схемы после слияния зависимых PR;
- добавить миграцию для outbox, inbox и предпочтений;
- реализовать централизованный сервис, API, keyset-пагинацию и проверку владения;
- добавить общую UI-точку входа и единый список;
- подключить один реальный источник события для проверки полного потока.

**Этап B — социальные события**
- подключить заявки и принятие дружбы к outbox;
- проверить совместимость с `user_friendships` и `user_blocks`;
- реализовать подавление и повторную проверку уведомлений при блокировке.

**Этап C — дни рождения**
- использовать существующее поле `users.date_of_birth` и `date_of_birth_visibility`, не дублируя данные;
- добавить IANA timezone для аккаунта;
- реализовать ежедневный worker и дедупликацию по году;
- проверить удаление/отзыв дружбы, смену видимости и отключение категории.

**Этап D — расширение**
- подключать новые типы событий только через центральный контракт;
- рассматривать системные уведомления Windows/email/push отдельно, но направлять их через общую маршрутизацию и предпочтения;
- не добавлять каналы без владельца доставки, обработки ошибок, повторов и тестов.

## 12. Критерии приёмки и тесты

### Безопасность
- Пользователь A не может получить, прочитать, скрыть или посчитать уведомления пользователя B даже при угадывании ID.
- Клиент не может передать recipient ID или произвольный destination URL.
- Удаление аккаунта удаляет его inbox; удаление инициатора не ломает уже сохранённую карточку и не раскрывает лишние данные.
- Блокировка исключает новые уведомления между сторонами и не оставляет доступного чувствительного payload.

### Корректность событий
- Одно доменное событие создаёт не более одной записи на получателя.
- Повторное выполнение outbox worker не создаёт дублей.
- Событие и доменное изменение не расходятся при сбое транзакции.
- Сбой worker не теряет событие; отложенные записи повторно обрабатываются с ограниченным backoff.
- Уведомления корректно сортируются, а keyset-пагинация не теряет и не дублирует строки при появлении новых записей.

### Настройки и дни рождения
- `full_date`, `day_month`, `reminder_only` и `hidden` дают разные ожидаемые результаты и не раскрывают лишний год.
- Напоминание получают только допустимые друзья, если получатель не отключил категорию.
- Блокировка, отзыв дружбы или изменение режима видимости не позволяют старому уведомлению продолжать раскрытие даты.
- Повторный запуск ежедневной задачи в одном году не создаёт повторных напоминаний.
- Переходы через полночь и разные часовые пояса проверяются отдельно.

### Интерфейс и API
- Вход в центр и число непрочитанных доступны из любого раздела.
- «Прочитать всё» и скрытие обновляют список и счётчик согласованно.
- Временные сообщения об ошибке/сохранении не попадают в постоянный inbox.
- API ограничивает размер страницы и использует стабильный курсор.
- Unit-, API integration- и PostgreSQL integration-тесты покрывают соответственно доменную логику, авторизацию/маршруты и ограничения/индексы/идемпотентность.

## 13. Решения, которые нужно подтвердить до реализации

1. Как долго хранить прочитанные уведомления и следует ли автоматически архивировать старые записи. До отдельного решения физическое удаление по TTL не включать.
2. Нужны ли отдельные Windows toast-уведомления в первой функциональной версии. Текущая спецификация считает их будущим каналом, а не частью обязательного MVP.
3. Какие категории пользователь может отключать самостоятельно и какие системные события должны оставаться обязательными.

До принятия этих решений можно реализовывать ядро inbox, не привязывая его к внешним каналам и не фиксируя необратимую политику хранения.
