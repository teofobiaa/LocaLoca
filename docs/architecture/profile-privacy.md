# Приватность профиля и отношения пользователей

Статус: реализуется в ветке `feature/profile-privacy-controls`, схема БД 015.

## Область текущей реализации

Настройки применяются отдельно к четырём существующим полям профиля:

- отображаемое имя (`users.display_name`);
- аватар (`user_avatars`);
- страна проживания (`users.residence_country`);
- город проживания (`users.residence_city`).

Логин — технический идентификатор входа: публичный endpoint профиля его не возвращает. Тема оформления и локальные настройки клиента не являются сведениями публичного профиля. Посещения, заметки, фотографии посещений, избранное и личные точки карты не становятся доступными другим пользователям в рамках этой функции; они остаются в существующих пользовательских API с проверкой владельца. Полная дата рождения также не включена в публичную модель этой ветки: в параллельной разработке она хранится отдельно и должна оставаться доступной только владельцу, пока не будет принято отдельное решение о более узком представлении (например, возрастная группа без даты).

## Категории доступа

Значения хранятся в `user_profile_visibility` и проверяются сервером:

- `private` — только владелец;
- `friends` — владелец и пользователи с подтверждённой взаимной дружбой;
- `registered` — любой пользователь с действующей авторизованной сессией LocaLoca.

«Заблокированные пользователи» — не вариант публикации. Блокировка — отдельный запрет, имеющий приоритет над любой настройкой. Если блок поставлен хотя бы в одну сторону, два аккаунта не видят профили друг друга и не могут создать дружбу, пока блок не снят.

Незарегистрированный и неавторизованный доступ не поддерживается.

## Начальные настройки

| Поле | Значение по умолчанию |
| --- | --- |
| Отображаемое имя | Все зарегистрированные |
| Аватар | Все зарегистрированные |
| Страна проживания | Только я |
| Город проживания | Только я |

Миграция 015 создаёт настройки для существующих аккаунтов. Триггер добавляет строку настроек при регистрации нового аккаунта. API также выполняет безопасное создание строки при чтении/обновлении настроек, чтобы пережить неполные старые данные.

## Модель дружбы и блокировки

`user_friendships` хранит одну запись на неупорядоченную пару аккаунтов. Меньший ID хранится в `user_low_id`, больший — в `user_high_id`. `requested_by_user_id` определяет отправителя ожидающего запроса; `status` принимает `pending` или `accepted`.

Повторный запрос от второго участника в ответ на ожидающий запрос автоматически подтверждает дружбу. Простое повторение запроса отправителем не создаёт дубликат. Принятие возможно только для входящего запроса.

`user_blocks` хранит одностороннюю блокировку. При блокировке в одной транзакции удаляется запись дружбы или ожидающий запрос для этой пары. Снятие блокировки не восстанавливает дружбу автоматически: участники должны отправить новый запрос.

## API

Настройки:
- `GET /api/me/profile/privacy` — получить свои настройки;
- `PUT /api/me/profile/privacy` — атомарно заменить настройки видимости существующих полей.

Профиль:
- `GET /api/users/{id}/profile` — получить только разрешённые поля чужого профиля;
- `GET /api/users/{id}/avatar?size=full|thumbnail` — получить аватар с той же проверкой приватности.

Поиск пользователей:
- `GET /api/users/search?login=<prefix>` — поиск по началу логина, без учёта регистра; требуется авторизация;
- поисковая строка должна содержать 3–50 допустимых символов; возвращается не более 20 аккаунтов;
- из выдачи исключаются текущий пользователь и аккаунты, заблокированные в любую сторону;
- логин возвращается всегда, отображаемое имя и наличие аватара — только согласно настройкам приватности;
- `relationshipStatus` принимает значения `none`, `outgoing_pending`, `incoming_pending`, `friends`;
- технический `userId` используется клиентом для существующих операций дружбы и не должен отображаться в интерфейсе;
- действует распределённый лимит 30 поисковых запросов в минуту на IP.

Дружба:
- `POST /api/users/{id}/friend-request` — отправить запрос;
- `GET /api/me/friend-requests` — входящие и исходящие ожидающие запросы;
- `POST /api/me/friend-requests/{id}/accept` — принять входящий запрос;
- `DELETE /api/me/friend-requests/{id}` — отменить или отклонить ожидающий запрос;
- `GET /api/me/friends` — список подтверждённых друзей;
- `DELETE /api/me/friends/{id}` — удалить из друзей.

Блокировки:
- `POST /api/users/{id}/block` — заблокировать;
- `GET /api/me/blocks` — список заблокированных текущим пользователем;
- `DELETE /api/me/blocks/{id}` — снять собственную блокировку.

Все перечисленные endpoints требуют действующую сессию. Профиль и аватар возвращают 404 для отсутствующего или заблокированного в любую сторону аккаунта, чтобы не раскрывать состояние отношений через отдельный ответ.

## Серверная проверка

Сокрытие данных в интерфейсе не считается контролем доступа. Endpoint профиля выбирает каждое поле через SQL-условие видимости и учитывает владельца, статус дружбы и блокировки. Endpoint аватара выполняет самостоятельную проверку; URL изображения не является обходным путём. Ответ аватара помечается `Cache-Control: private, no-store`.

## Миграция и права

Для существующей базы последовательно выполнить миграции 015, 016 и 017. Миграция 017 добавляет индекс префиксного поиска по логину. Затем выполнить `database/security/06_update_runtime_permissions.sql` от имени администратора, если runtime-роль уже существует.

Если runtime-роль ещё не создана, выполнить `database/security/05_create_app_role.sql` после миграции 015. Проверка `/ready` требует новую схему и DML-права на три таблицы отношений/настроек.

Для новой базы использовать полный снимок `database/schema/01_schema.sql` версии 013, затем применить миграцию 014. Снимок 013 намеренно не переписывается.

## Текущие ограничения

В этой итерации реализованы модель, серверные endpoints и элементы интерфейса для изменения видимости. Отдельный интерфейс поиска пользователей, просмотра чужих профилей, управления запросами дружбы и списком блокировок пока не добавлен. API-операции для этих сценариев уже подготовлены.

Пользовательские списки аудитории не входят в миграцию 014 и не реализованы. Их проектное описание хранится в [будущем этапе пользовательских списков](../roadmap/future/user-defined-audience-lists.md).
