# Пользовательские списки аудитории

Статус: будущий этап, НЕ реализован в текущей ветке.

## Цель

Разрешить владельцу профиля создавать собственные именованные группы пользователей, например «Близкие», «Семья», «Колледж» или «Коллеги», и выбирать такую группу в качестве аудитории отдельных полей профиля.

Это дополнение к существующим вариантам «Только я», «Друзья» и «Все зарегистрированные», а не новая роль аккаунта.

## Предлагаемое поведение

- Каждый список принадлежит одному владельцу и виден только ему.
- Владелец создаёт, переименовывает и удаляет свои списки, а также добавляет и исключает участников.
- В списке могут состоять только зарегистрированные аккаунты LocaLoca.
- Добавление в список само по себе не создаёт дружбу и не требует взаимного добавления.
- Пользователь может состоять в нескольких списках одного владельца.
- Для поля, доступного нескольким аудиториям, достаточно соответствовать хотя бы одной из них (логика OR).
- Владелец всегда видит собственные поля.
- Блокировка в любом направлении всегда запрещает доступ, даже если заблокированный аккаунт состоит в разрешённом списке.
- Снятие блокировки не должно автоматически возвращать аккаунт в списки, из которых он был исключён отдельным действием.

## Возможная модель данных

На этапе проектирования рассмотреть отдельные таблицы, например:

- `user_audience_lists`: идентификатор списка, владелец, имя, даты создания и изменения;
- `user_audience_list_members`: список и ID участника, дата добавления.

Нужны уникальность имени списка в пределах владельца, уникальность пары (список, участник), внешние ключи с каскадным удалением, индексы по владельцу и участнику, ограничения на длину имени и число списков/участников. Конкретные лимиты следует определить до миграции.

## Правила безопасности

- Нельзя доверять ID списка, пришедшему от клиента: каждый запрос обязан проверять, что список принадлежит текущему владельцу профиля.
- Нельзя раскрывать участникам полный состав чужих списков.
- Участие в списке одного профиля не даёт доступа к сведениям других профилей.
- Нельзя разрешать списку обходить блокировку.
- Проверка должна происходить на API/в запросе к БД, а не только в интерфейсе.
- Следует проверить, не позволяют ли ответы API определять, в каких пользовательских списках состоит аккаунт.

## Что потребуется реализовать

1. Миграция БД с таблицами списков и участников, индексами и ограничениями.
2. API для CRUD списков и управления участниками с проверкой владельца.
3. Расширение схемы настроек видимости, чтобы поле могло быть доступно нескольким аудиториям.
4. Серверный evaluator аудитории с единым правилом: владелец ИЛИ разрешённая аудитория, но никогда не заблокированная пара.
5. Интерфейс управления списками и выбора аудитории для каждого поля профиля.
6. Интеграционные тесты на несколько списков, удаление участников, удаление списка, блокировки и попытки доступа к чужим спискам.

До выполнения отдельной миграции пользовательские списки не должны появляться среди доступных вариантов настроек.
