# База данных Loca Loca

Каталог `database/` содержит SQL-файлы **одной PostgreSQL-базы Loca Loca**: актуальную схему, справочные данные, миграции и настройки прав. Скрипты не входят в Windows-установщик и не исполняются автоматически при запуске API. Их применяет администратор базы через Supabase SQL Editor или другой доверенный PostgreSQL-клиент.

## Версии и состав SQL

Единый реестр версий и SHA-256 контрольных сумм находится в [migrations/manifest.json](migrations/manifest.json). CI проверяет, что опубликованные SQL-файлы соответствуют реестру. Уже опубликованные миграции считаются неизменяемыми: исправления и новые изменения оформляются новым номером, а не переписыванием старого файла.

| Раздел | Назначение |
| --- | --- |
| `schema/` | Полный снимок актуальной схемы для новой пустой базы |
| `seed/` | Начальный набор справочных данных; версионируется отдельно от структуры |
| `migrations/` | Упорядоченные изменения схемы и журнал их применения |
| `security/` | Однократное создание runtime-роли и повторяемое обновление её прав |
| `audits/` | Диагностические SQL-запросы для проверки доступа |

Текущая версия схемы — **020**. Файл `schema/01_schema.sql` сохраняется как baseline **013** для тестирования обновления старых установок. Для новых установок используется `schema/02_schema_v20.sql` — полный снимок актуальной структуры **020**: в нём уже есть изменения из миграций 003, 004, 007, 008, 009, 010, 011, 012 и 013, включая серверные сессии, индексы карты, поля места проживания, распределённые счётчики авторизации и хранилище аватаров. Миграции 014–020 остаются отдельными неизменяемыми файлами для обновления существующих баз с baseline 013. Для новой базы их итоговое состояние уже включено в baseline 020. Ни один из этих baseline-файлов не является скриптом обновления существующей базы.

Для fresh-install baseline 020 массив `freshInstallBaseline.includesSchemaMigrations` в manifest перечисляет только структурные миграции 003–004 и 007–020 (16 версий). В `localoca_schema_migrations` дополнительно присутствует техническая запись `(1, 'initial_schema', 'baseline')`: она обозначает исходную схему и не является отдельной миграцией из manifest. Поэтому полный ledger содержит 17 записей: 16 версий manifest плюс один маркер `initial_schema`. Интеграционный тест сверяет все версии manifest с ledger без версии 1 и отдельно проверяет наличие маркера; не добавляй версию 1 в список `includesSchemaMigrations` и не удаляй эту запись из baseline.

Таблица `public.localoca_schema_migrations` хранит номера структурных миграций, имена, время и источник записи:
- `baseline` — объект включён в полный снимок новой схемы;
- `migration` — файл миграции выполнился и записал свою версию;
- `adopted` — bootstrap обнаружил соответствующие объекты в уже существующей базе.

Начальные данные из `seed/02_seed.sql` и действия с ролью из `security/` не являются структурными миграциями и в эту таблицу не записываются.

## Аватары пользователей

Каждому аккаунту соответствует не более одного аватара. API принимает JPG, PNG, WEBP, BMP и GIF размером до 5 МиБ, повторно декодирует изображение и сверяет фактический формат с расширением. Общий валидатор ограничивает размеры, число кадров и объём декодируемых пикселей. GIF принимается как статичное изображение первого кадра.

Сервер не хранит исходный загруженный файл. Он формирует оптимизированный JPEG с максимальной стороной 512 пикселей и квадратную миниатюру 96 × 96 пикселей. В таблице public.user_avatars хранятся оба результата; ограничения БД не позволяют превысить 1 МиБ для основного изображения и 128 КиБ для миниатюры. Загрузка использует UPSERT, поэтому замена не создаёт вторую запись. Получение и удаление выполняются только для текущей авторизованной учётной записи.

## Перед запуском SQL

1. Убедись, что выбран нужный Supabase-проект и база.
2. Сделай резервную копию рабочей базы перед миграциями.
3. Не запускай полный снимок `schema/01_schema.sql` или seed поверх рабочей базы.
4. Выполняй административные действия под административной ролью, API подключай отдельной ролью `localoca_app`.
5. Не помещай реальные пароли и строки подключения в Git, README, SQL-файлы или установщик.

Приложение использует собственную таблицу `users`; это не Supabase Auth. Для сервера используется Supabase Session Pooler, роль вида `localoca_app.<project-ref>` и TLS.

## Создание новой базы

Для новой пустой базы используй актуальный baseline 020. Baseline 013 оставлен для совместимости и проверки обновления существующих установок.

На пустой базе выполни файлы строго в таком порядке:

| Шаг | Файл | Действие |
| --- | --- | --- |
| 1 | [schema/02_schema_v20.sql](schema/02_schema_v20.sql) | Создаёт полный снимок схемы версии 020 и заполняет журнал версиями 001, 003–004 и 007–020, включёнными в baseline. |
| 2 | [seed/02_seed.sql](seed/02_seed.sql) | Добавляет справочные категории, страны, города и достопримечательности. |
| 3 | [security/05_create_app_role.sql](security/05_create_app_role.sql) | Создаёт отдельную runtime-роль. Пароль-заглушку нужно заменить на уникальный случайный пароль. |
| 4 | [security/06_update_runtime_permissions.sql](security/06_update_runtime_permissions.sql) | Настраивает актуальные RLS-политики и минимальные права runtime-роли для схемы v020. |

Для новой базы **не запускай** миграции 003–020: их итоговое состояние уже включено в baseline 020. После создания runtime-роли обязательно выполни повторяемый `06_update_runtime_permissions.sql`: он применяет RLS и grants, соответствующие версиям 017–020. Скрипт 05 использует `CREATE ROLE` и предназначен для однократного запуска. Seed выполняется после baseline и до создания роли.

## Обновление существующей базы

Не запускай `schema/01_schema.sql` и полный seed поверх рабочей базы. Сначала создай или восстанови журнал версий:

1. Выполни [migrations/00_migration_history.sql](migrations/00_migration_history.sql) под администратором БД. Скрипт создаёт журнал и отмечает только те версии, чьи таблицы, столбцы, ограничения и индексы уже присутствуют. Он не меняет прикладные таблицы и данные; повторное выполнение безопасно.
2. Посмотри фактически зарегистрированные версии:

```sql
SELECT version, name, source, applied_at
FROM public.localoca_schema_migrations
ORDER BY version;
```

3. Сверь результат с реестром и выполняй только отсутствующие миграции, строго по возрастанию номера:

Запускай bootstrap до и после серии миграций. Если проверка объекта не прошла, версия не будет зарегистрирована.

### Отдельно: права runtime-роли

Версии 005 и 006 — **операции безопасности**, а не изменения структуры таблиц, поэтому они не попадают в `localoca_schema_migrations`.

- [security/05_create_app_role.sql](security/05_create_app_role.sql) запускается только если роли `localoca_app` ещё нет. Выполняй его после создания полного снимка схемы 013 или после применения всех необходимых миграций существующей базы, включая 013. Выдача прав на `user_sessions`, `auth_rate_limit_counters` и `user_avatars` условная: она выполняется, только если соответствующие таблицы уже существуют.
- [security/06_update_runtime_permissions.sql](security/06_update_runtime_permissions.sql) запускается после миграции 020, если роль уже существует и ей нужно привести права к текущей схеме. Скрипт повторяемый: он пересоздаёт утверждённые RLS-политики, отзывает лишние grants и возвращает только разрешённые табличные, sequence- и column-level права.
- Миграции 014 и 015 создают приватные таблицы и выдают права `localoca_app`, если роль уже существует. Миграция 017 пересобирает RLS-политики и grants по принципу минимальных привилегий; `BYPASSRLS` не используется. Миграция 019 отдельно возвращает column-level `UPDATE` только для `users.password_hash`, необходимый для постепенного обновления хешей паролей.

### Неизменяемость и контроль версий

Не редактируй опубликованные файлы 003/004/007/008/009/010 ради исправления старой миграции: checksum в manifest и CI обнаружат такое изменение. Для будущих миграций используй следующий свободный номер, записывай его в `localoca_schema_migrations` в конце нового скрипта и обновляй реестр. Если SQL-файл завершился ошибкой до записи версии, сначала проверь фактическое состояние БД, затем безопасно повтори миграцию или подготовь отдельную corrective migration.

Наличие версии в Git не доказывает её применение в конкретной базе. Источник истины для существующей базы — `localoca_schema_migrations` плюс фактическая проверка объектов PostgreSQL. Seed и роль проверяются отдельно.

## Проверки совместимости старой схемы

Проверка API `/ready` продолжает требовать столбцы хранения фотографий и таблицу `user_sessions`, а чтение фотографий сохраняет совместимость со старыми файловыми записями. Эти проверки намеренно не удаляются в рамках упорядочивания миграций. Отказ от старой схемы допустим только после отдельного решения о прекращении её поддержки, проверки всех используемых баз и согласованного срока миграции.

## Оценка хранения фотографий

Архитектурное решение и сценарии перехода с PostgreSQL `bytea` на объектное хранилище описаны в [PHOTO-STORAGE-ASSESSMENT.md](PHOTO-STORAGE-ASSESSMENT.md). Текущая рекомендация — оставить `bytea` до появления измеримых причин для миграции; оценка включает стоимость, резервное копирование, миниатюры и план переноса.

## Место проживания, локальные рекомендации и география аудитории

Миграция 011 добавляет nullable-поля `users.residence_country` и `users.residence_city`. Значения вводит сам пользователь; для старых аккаунтов они остаются пустыми и не определяются по истории посещений. Можно указать только страну или страну вместе с городом; город без страны не принимается. Точный адрес и координаты не собираются.

### Локальные рекомендации

Авторизованный endpoint `GET /api/me/recommendations?take=8` использует место проживания из профиля и текущий каталог достопримечательностей:

- сначала выдаются непосещённые места в указанном городе и стране;
- затем — непосещённые места в остальных городах этой страны;
- при заполненной только стране выдаются непосещённые места по всей стране;
- посещения проверяются по паре `user_id + attraction_id`, данные других аккаунтов не влияют на выдачу;
- размер ответа ограничен: по умолчанию 8, допустимый диапазон — от 1 до 20;
- при пустом месте проживания endpoint возвращает пустой список.

Сопоставление названий страны и города регистронезависимое и игнорирует пробелы по краям. Это прозрачная rule-based подборка по существующему каталогу, а не ML-рейтинг: она не выдумывает места и не обещает популярность. Если подходящих записей в каталоге нет, приложение сообщает об этом и предлагает проверить место проживания или открыть полный каталог. Новая таблица и миграция для рекомендаций не нужны: используются существующие справочник, профиль и индекс посещений.

### Агрегированная география аудитории

Для внутреннего анализа предназначен read-only отчёт `database/analytics/01_audience_geography.sql`. Его запускает администратор вручную в Supabase SQL Editor или другом доверенном административном SQL-клиенте. Отчёт группирует только self-reported страну и город профиля; география посещённых достопримечательностей в него не попадает. Логины, user_id, адреса и координаты не выводятся. Публичного API для этой статистики нет, runtime-роль `localoca_app` не получает дополнительных прав.

Механизмы подавления малых групп:
- строка страны показывается только при наличии не менее 5 профилей;
- городская разбивка страны публикуется целиком, только если каждая городская группа содержит не менее 5 профилей и за каждой группой остаётся не менее 5 профилей;
- количество профилей без указанного города должно быть равно нулю или не меньше 5;
- если хотя бы одна группа или остаток меньше 5, все городские строки этой страны скрываются; малые группы не объединяются в «прочее».

Это снижает риск раскрытия малочисленных групп через прямое чтение или вычитание агрегатов. Отчёт предназначен для статистического обзора, а не для восстановления данных отдельных аккаунтов.

## Runtime-роль и секреты подключения

API не должно подключаться как владелец базы или административная роль `postgres`. Используй отдельную роль `localoca_app` с минимально необходимыми разрешениями.

- Пароль, указанный в `05_create_app_role.sql`, должен быть уникальным и не совпадать с паролем владельца проекта.
- Строка подключения развёрнутого API хранится в Render как секрет `LOCA_DB_CONNECTION`.
- Секрет подписи сессий хранится в Render как `LOCA_SESSION_SECRET`.
- Для локальной разработки может использоваться `%LOCALAPPDATA%\LocaLoca\server-config.json`; пароль в актуальном формате защищён Windows DPAPI с областью `CurrentUser`.

Не коммить реальные значения этих параметров. Если секрет попал в историю Git, считай его раскрытым и замени, даже если последняя версия файла уже очищена.

Проверка API `/ready` подтверждает доступность базы, наличие нужных объектов схемы и runtime-разрешений. Она не запускает SQL-миграции и не исправляет конфигурацию автоматически.

## Проверка доступа через Supabase Data API

Для диагностики прямого доступа к таблицам через Supabase Data API используй [audits/check_supabase_data_api_access.sql](audits/check_supabase_data_api_access.sql).

Запрос показывает:

- состояние Row Level Security (RLS);
- прямые права ролей `anon`, `authenticated` и `PUBLIC` на таблицы и представления;
- права `EXECUTE` на функции и процедуры;
- политики RLS;
- default privileges для будущих объектов.

Это **только диагностический запрос**: он не изменяет таблицы, права или политики. Запускай его в Supabase SQL Editor под ролью с достаточными правами для просмотра сведений.

При анализе результата:
- если RLS выключен и публичные роли имеют доступ к пользовательским таблицам, проверь возможность чтения или изменения данных;
- если RLS включён, изучи каждую политику и разрешённые ею операции;
- проверь default privileges: новые объекты могут автоматически получать права;
- не выполняй массовые `REVOKE` или `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` без анализа последствий.

Сервер Loca Loca подключается к PostgreSQL через Npgsql под ролью `localoca_app`. Изменения прав для Supabase Data API не должны случайно лишить сервер нужных разрешений.

## Экспорт справочного каталога

Скрипт [tools/Export-AttractionsSeed.ps1](../tools/Export-AttractionsSeed.ps1) экспортирует справочник достопримечательностей из доступной разработчику базы в `seed/02_seed.sql`.

Скрипт использует `LOCA_DB_CONNECTION` или локальный файл `%LOCALAPPDATA%\LocaLoca\server-config.json`; поддерживаются старый формат и новый DPAPI-формат. Расшифровать DPAPI-пароль может только та же учётная запись Windows, которая создала конфигурацию. На компьютере должны быть установлены PostgreSQL Command Line Tools, включая `psql`.

## Распределённые ограничения авторизации

Миграция 012 создаёт `public.auth_rate_limit_counters`. API использует атомарный PostgreSQL UPSERT для общих фиксированных 60-секундных окон: 5 попыток входа, 3 регистрации и 10 запросов выхода на один IP. Все экземпляры API используют одну таблицу; счётчики не теряются при перезапуске процесса. Истёкшие строки удаляются при следующих запросах авторизации не чаще одного раза в пять минут на экземпляр API. В Render клиентский IP определяется по `CF-Connecting-IP`; `X-Forwarded-For` не используется.
