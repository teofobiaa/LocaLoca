# Структура PostgreSQL

В этой папке находятся SQL-скрипты **одной базы данных Loca Loca**, а не отдельные базы. Они разделены по назначению, чтобы схема, наполнение, обновления и настройки доступа не лежали вперемешку.

SQL-файлы не включаются в Windows-установщик и не исполняются автоматически при старте API. Их применяет администратор PostgreSQL в Supabase SQL Editor.

## Каталоги

| Каталог | Назначение |
| --- | --- |
| `schema/` | Полная актуальная схема новой базы |
| `seed/` | Начальные справочные данные каталога |
| `migrations/` | Изменения для баз, созданных по более ранним версиям |
| `security/` | Создание отдельной runtime-роли приложения |

## Новая база данных

Для пустого Supabase-проекта выполни:

1. [schema/01_schema.sql](schema/01_schema.sql) — создаёт актуальные таблицы, связи, ограничения, индексы и представление. В этой версии уже есть wishlist, личные точки карты и столбцы `bytea` для фотографий.
2. [seed/02_seed.sql](seed/02_seed.sql) — добавляет справочные категории, страны, города и достопримечательности.
3. [security/05_create_app_role.sql](security/05_create_app_role.sql) — создаёт отдельную роль с минимально необходимыми правами. **До запуска замени пароль-заглушку** на уникальный случайный пароль и сохрани его в защищённом хранилище.

После этого настрой API. Для новой базы миграции `03`, `04`, `06` и `07` не нужны: их изменения уже включены в актуальную схему и скрипт создания роли.

## Существующая база

Не запускай полную схему и seed поверх рабочей базы. Сначала проверь её фактическое состояние и применяй только отсутствующие изменения:

- [migrations/03_migrate_wishlist.sql](migrations/03_migrate_wishlist.sql) — добавляет wishlist, если таблицы ещё нет.
- [migrations/04_migrate_user_map_places.sql](migrations/04_migrate_user_map_places.sql) — добавляет личные точки карты и связанные фотографии. Эту миграцию нужно выполнить до миграции хранения фотографий, если таблицы личных точек ещё нет.
- [security/05_create_app_role.sql](security/05_create_app_role.sql) — запускается **только если роль `localoca_app` ещё не создана**. В скрипте используется `CREATE ROLE`, повторный запуск завершится ошибкой.
- [security/06_update_runtime_permissions.sql](security/06_update_runtime_permissions.sql) — обновляет права уже существующей роли: изменение `users.display_name`, CRUD для личных точек карты и доступ к их identity-последовательностям. Запускается после миграции `04`; повторное выполнение безопасно.
- [migrations/07_migrate_photo_storage.sql](migrations/07_migrate_photo_storage.sql) — добавляет/проверяет столбцы `image_data` и `content_type`, ограничения размера и типа изображений, а также повторно выдаёт runtime-роли необходимые права на фотографии. Для старой базы выполни её **до развёртывания версии API, которая требует хранения фотографий в PostgreSQL**.

Скрипты `03`, `04`, `06` и `07` рассчитаны на повторное применение в пределах описанной схемы; скрипт `05` — нет. Не считай файл миграции доказательством того, что она уже применена: проверяй схему в самой базе.

## Runtime-права и подключение

Приложение должно подключаться ролью `localoca_app`, а не владельцем базы и не административной ролью `postgres`. Для Supabase Session Pooler имя пользователя имеет вид `localoca_app.<project-ref>`.

После миграции `04`, если роль `localoca_app` существовала до появления личных точек карты, обязательно выполни скрипт `06`, чтобы выдать ей недостающие права. Для новой роли эти разрешения уже входят в `05`.

Пароль для SQL-скрипта `05` не должен совпадать с паролем владельца Supabase. Не сохраняй реальный пароль в Git, README, SQL-скриптах или установщике. Строка подключения развёрнутого API хранится в Render как секрет `LOCA_DB_CONNECTION`.

Проверка `/ready` подтверждает доступность БД, нужных колонок фотографий и runtime-разрешений. Она не применяет миграции автоматически.

## Проверка доступа через Supabase Data API

Если в старых версиях приложения использовался Supabase publishable/anon key, проверь, что таблицы нельзя читать или изменять напрямую через Data API в обход облачного Loca Loca API.

Для этого предназначен [audits/check_supabase_data_api_access.sql](audits/check_supabase_data_api_access.sql). Это **только диагностический запрос**: он показывает состояние RLS, прямые права `anon`, `authenticated` и `PUBLIC` на таблицы/представления, права `EXECUTE` на функции и процедуры, политики RLS и default privileges для будущих объектов. Он ничего не изменяет.

Запусти его в Supabase SQL Editor под ролью администратора и изучи результат:
- если RLS выключен и `anon`, `authenticated` или `PUBLIC` имеют права на пользовательские таблицы, проверь потенциальную доступность данных;
- если RLS включён, проверь существующие политики и то, какие операции они разрешают;
- проверь default privileges отдельно: новые таблицы могут получать права автоматически;
- не запускай массовый `REVOKE` или `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` без анализа. Приложение подключается к PostgreSQL через Npgsql под ролью `localoca_app`; сначала убедись, что изменения не сломают этот серверный доступ.

Текущий Windows-клиент использует облачный API, а не Supabase Data API. Сам publishable/anon key не является паролем БД или service-role секретом, но его публичность не заменяет RLS и корректные grants.

## Экспорт стартового каталога

Скрипт [tools/Export-AttractionsSeed.ps1](../tools/Export-AttractionsSeed.ps1) выгружает справочник из доступной разработчику базы в `seed/02_seed.sql`. Он принимает строку `LOCA_DB_CONNECTION` либо читает локальный `%LOCALAPPDATA%\LocaLoca\server-config.json`, включая новый DPAPI-формат. Расшифровка возможна только под той же учётной записью Windows, которая создала конфигурацию. Требуется PostgreSQL Command Line Tools (`psql`).
