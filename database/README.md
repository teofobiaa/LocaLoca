# База данных Loca Loca

Каталог `database/` содержит SQL-файлы **одной PostgreSQL-базы Loca Loca**: актуальную схему, справочные данные, миграции и настройки прав. Скрипты не входят в Windows-установщик и не исполняются автоматически при запуске API. Их применяет администратор базы через Supabase SQL Editor или другой доверенный PostgreSQL-клиент.

## Версии и состав SQL

Единый реестр версий и SHA-256 контрольных сумм находится в [migrations/manifest.json](migrations/manifest.json). CI проверяет, что опубликованные SQL-файлы соответствуют реестру. Уже опубликованные миграции считаются неизменяемыми: исправления и новые изменения оформляются новым номером, а не переписыванием старого файла.

| Раздел | Назначение |
| --- | --- |
| `schema/` | Полный снимок актуальной схемы для новой пустой базы |
| `seed/` | Начальный набор справочных данных; версионируется отдельно от структуры |
| `migrations/` | Упорядоченные изменения схемы и журнал их применения |
| `security/` | Однократное создание runtime-роли и повторяемое обновление её прав |
| `audits/` | Диагностические SQL-запросы для проверки доступа |

Текущая версия схемы — **009**. Файл `schema/01_schema.sql` — полный снимок этой версии: в нём уже есть изменения из миграций 003, 004, 007, 008 и 009, включая серверные сессии и индексы карты. Это не скрипт обновления существующей базы.

Таблица `public.localoca_schema_migrations` хранит номера структурных миграций, имена, время и источник записи:
- `baseline` — объект включён в полный снимок новой схемы;
- `migration` — файл миграции выполнился и записал свою версию;
- `adopted` — bootstrap обнаружил соответствующие объекты в уже существующей базе.

Начальные данные из `seed/02_seed.sql` и действия с ролью из `security/` не являются структурными миграциями и в эту таблицу не записываются.

## Перед запуском SQL

1. Убедись, что выбран нужный Supabase-проект и база.
2. Сделай резервную копию рабочей базы перед миграциями.
3. Не запускай полный снимок `schema/01_schema.sql` или seed поверх рабочей базы.
4. Выполняй административные действия под административной ролью, API подключай отдельной ролью `localoca_app`.
5. Не помещай реальные пароли и строки подключения в Git, README, SQL-файлы или установщик.

Приложение использует собственную таблицу `users`; это не Supabase Auth. Для сервера используется Supabase Session Pooler, роль вида `localoca_app.<project-ref>` и TLS.

## Создание новой базы

На пустой базе выполни файлы строго в таком порядке:

| Шаг | Файл | Действие |
| --- | --- | --- |
| 1 | [schema/01_schema.sql](schema/01_schema.sql) | Создаёт полный снимок схемы версии 009 и заполняет журнал базовыми версиями 001, 003, 004, 007, 008 и 009. |
| 2 | [seed/02_seed.sql](seed/02_seed.sql) | Добавляет справочные категории, страны, города и достопримечательности. |
| 3 | [security/05_create_app_role.sql](security/05_create_app_role.sql) | Создаёт runtime-роль с минимальными правами, включая доступ к `user_sessions`. Пароль-заглушку нужно заменить на уникальный случайный пароль. |

Для новой базы **не запускай** миграции 003, 004, 007, 008 и 009: их изменения уже есть в полном снимке схемы. Также не запускай `06_update_runtime_permissions.sql`, если роль только что создана текущим скриптом 05. Скрипт 05 использует `CREATE ROLE` и предназначен для однократного запуска.

## Обновление существующей базы

Не запускай `schema/01_schema.sql` и полный seed поверх рабочей базы. Сначала создай или восстанови журнал версий:

1. Выполни [migrations/00_migration_history.sql](migrations/00_migration_history.sql) под администратором БД. Скрипт создаёт журнал и отмечает только те версии, чьи таблицы, столбцы, ограничения и индексы уже присутствуют. Он не меняет прикладные таблицы и данные; повторное выполнение безопасно.
2. Посмотри фактически зарегистрированные версии:

```sql
SELECT version, name, source, applied_at
FROM public.localoca_schema_migrations
ORDER BY version;
```

3. Сверь результат с реестром и выполняй только отсутствующие миграции, строго по возрастанию номера:

| Версия | Файл | Назначение |
| --- | --- | --- |
| 003 | [migrations/03_migrate_wishlist.sql](migrations/03_migrate_wishlist.sql) | Список желаемых мест |
| 004 | [migrations/04_migrate_user_map_places.sql](migrations/04_migrate_user_map_places.sql) | Личные точки карты и их фотографии |
| 007 | [migrations/07_migrate_photo_storage.sql](migrations/07_migrate_photo_storage.sql) | Хранение бинарных данных фотографий в PostgreSQL и ограничения MIME/размера |
| 008 | [migrations/08_server_sessions.sql](migrations/08_server_sessions.sql) | Постоянное хранилище серверных сессий |
| 009 | [migrations/09_map_marker_viewport_indexes.sql](migrations/09_map_marker_viewport_indexes.sql) | Индексы координат для запросов по видимой области карты |

Каждый файл 003/004/007/008/009 записывает свою версию в `localoca_schema_migrations` после выполнения изменений. Повторные запуски этих файлов безопасны для описанной схемы; уже зарегистрированную версию можно сверять по журналу, а не определять по имени файла на глаз.

### Отдельно: права runtime-роли

Версии 005 и 006 — **операции безопасности**, а не изменения структуры таблиц, поэтому они не попадают в `localoca_schema_migrations`.

- [security/05_create_app_role.sql](security/05_create_app_role.sql) запускается только если роли `localoca_app` ещё нет. Выполняй его после создания необходимых таблиц версии 004. Выдача прав на `user_sessions` условная: она выполняется, только если таблица уже существует.
- [security/06_update_runtime_permissions.sql](security/06_update_runtime_permissions.sql) запускается, если роль уже существует и ей нужно обновить права. Он безопасен до и после миграции 008; после создания сессий повторный запуск выдаёт недостающие разрешения.
- Миграция 008 тоже выдаёт права на `user_sessions`, если роль уже существует.

### Неизменяемость и контроль версий

Не редактируй опубликованные файлы 003/004/007/008/009 ради исправления старой миграции: checksum в manifest и CI обнаружат такое изменение. Добавляй следующий свободный номер и обновляй реестр. Если SQL-файл завершился ошибкой до записи версии, сначала проверь фактическое состояние БД, затем безопасно повтори миграцию или подготовь отдельную corrective migration.

Наличие версии в Git не доказывает её применение в конкретной базе. Источник истины для существующей базы — `localoca_schema_migrations` плюс фактическая проверка объектов PostgreSQL. Seed и роль проверяются отдельно.

## Проверки совместимости старой схемы

Проверка API `/ready` продолжает требовать столбцы хранения фотографий и таблицу `user_sessions`, а чтение фотографий сохраняет совместимость со старыми файловыми записями. Эти проверки намеренно не удаляются в рамках упорядочивания миграций. Отказ от старой схемы допустим только после отдельного решения о прекращении её поддержки, проверки всех используемых баз и согласованного срока миграции.

## Runtime-роль и секреты подключения

API не должно подключаться как владелец базы или административная роль `postgres`. Используй отдельную роль `localoca_app` с минимально необходимыми разрешениями.

- Пароль, указанный в `05_create_app_role.sql`, должен быть уникальным и не совпадать с паролем владельца проекта.
- Строка подключения развёрнутого API хранится в Render как секрет `LOCA_DB_CONNECTION`.
- Секрет подписи сессий хранится в Render как `LOCA_SESSION_SECRET`.
- Для локальной разработки может использоваться `%LOCALAPPDATA%\LocaLoca\server-config.json`; пароль в актуальном формате защищён Windows DPAPI с областью `CurrentUser`.

Не коммить реальные значения этих параметров. Если секрет попал в историю Git, считай его раскрытым и замени, даже если последняя версия файла уже очищена.

Проверка API `/ready` подтверждает доступность базы, наличие нужных объектов схемы и runtime-разрешений. Она не запускает SQL-миграции и не исправляет конфигурацию автоматически.

## Проверка доступа через Supabase Data API

Для диагностики прямого доступа к таблицам через Supabase Data API используй [audits/check_supabase_data_api_access.sql](audits/check_supabase_data_api_access.sql).

Запрос показывает:

- состояние Row Level Security (RLS);
- прямые права ролей `anon`, `authenticated` и `PUBLIC` на таблицы и представления;
- права `EXECUTE` на функции и процедуры;
- политики RLS;
- default privileges для будущих объектов.

Это **только диагностический запрос**: он не изменяет таблицы, права или политики. Запускай его в Supabase SQL Editor под ролью с достаточными правами для просмотра сведений.

При анализе результата:
- если RLS выключен и публичные роли имеют доступ к пользовательским таблицам, проверь возможность чтения или изменения данных;
- если RLS включён, изучи каждую политику и разрешённые ею операции;
- проверь default privileges: новые объекты могут автоматически получать права;
- не выполняй массовые `REVOKE` или `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` без анализа последствий.

Сервер Loca Loca подключается к PostgreSQL через Npgsql под ролью `localoca_app`. Изменения прав для Supabase Data API не должны случайно лишить сервер нужных разрешений.

## Экспорт справочного каталога

Скрипт [tools/Export-AttractionsSeed.ps1](../tools/Export-AttractionsSeed.ps1) экспортирует справочник достопримечательностей из доступной разработчику базы в `seed/02_seed.sql`.

Скрипт использует `LOCA_DB_CONNECTION` или локальный файл `%LOCALAPPDATA%\LocaLoca\server-config.json`; поддерживаются старый формат и новый DPAPI-формат. Расшифровать DPAPI-пароль может только та же учётная запись Windows, которая создала конфигурацию. На компьютере должны быть установлены PostgreSQL Command Line Tools, включая `psql`.
