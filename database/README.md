# База данных Loca Loca

Каталог `database/` содержит SQL-файлы **одной PostgreSQL-базы Loca Loca**: актуальную схему, справочные данные, миграции и настройки прав. Скрипты не входят в Windows-установщик и не исполняются автоматически при запуске API. Их применяет администратор базы через Supabase SQL Editor или другой доверенный PostgreSQL-клиент.

## Состав каталога

| Каталог | Назначение |
| --- | --- |
| `schema/` | Полная актуальная схема для новой пустой базы |
| `seed/` | Начальные справочные данные каталога |
| `migrations/` | Пошаговое обновление ранее созданной базы |
| `security/` | Создание и обновление runtime-разрешений приложения |
| `audits/` | Диагностические SQL-запросы для проверки доступа |

## Перед запуском SQL

1. Убедись, что выбран нужный Supabase-проект и база.
2. Сделай резервную копию рабочей базы перед миграциями.
3. Проверь текущую схему: не запускай полную схему новой базы поверх существующей.
4. Выполняй административные действия под административной ролью, а само API подключай отдельной ролью `localoca_app`.
5. Не помещай настоящий пароль роли или строку подключения в Git, README, скрипты, установщик и публичные сообщения.

Приложение использует собственную таблицу `users`; это не Supabase Auth. Для подключения сервера к Supabase используется Session Pooler, имя роли имеет вид `localoca_app.<project-ref>`, соединение должно использовать TLS.

## Создание новой базы

Для пустой базы применяй файлы в следующем порядке:

| Шаг | Файл | Действие |
| --- | --- | --- |
| 1 | [schema/01_schema.sql](schema/01_schema.sql) | Создаёт актуальные таблицы, связи, ограничения, индексы и представление. В схему включены wishlist, личные точки карты и столбцы `bytea` для фотографий. |
| 2 | [seed/02_seed.sql](seed/02_seed.sql) | Добавляет справочные категории, страны, города и достопримечательности. |
| 3 | [security/05_create_app_role.sql](security/05_create_app_role.sql) | Создаёт отдельную runtime-роль с минимально необходимыми правами. Перед запуском замени пароль-заглушку на уникальный случайный пароль. |
| 4 | [migrations/08_server_sessions.sql](migrations/08_server_sessions.sql) | Создаёт постоянное хранилище серверных сессий и выдаёт права роли, если она уже создана. |

Для новой базы миграции `03`, `04`, `06` и `07` не требуются: их изменения уже входят в актуальную схему и актуальный скрипт создания роли. Не запускай `05_create_app_role.sql` повторно: он использует `CREATE ROLE` и не предназначен для повторного выполнения.

## Обновление существующей базы

Не запускай `01_schema.sql` и полный seed поверх рабочей базы. Сначала выясни, какие изменения уже применены, затем выполняй только недостающие миграции.

| Файл | Когда нужен | Повторный запуск |
| --- | --- | --- |
| [migrations/03_migrate_wishlist.sql](migrations/03_migrate_wishlist.sql) | Если в старой базе ещё нет wishlist | Рассчитан на повторное применение |
| [migrations/04_migrate_user_map_places.sql](migrations/04_migrate_user_map_places.sql) | Если в старой базе ещё нет личных точек карты и связанных фотографий | Рассчитан на повторное применение |
| [security/05_create_app_role.sql](security/05_create_app_role.sql) | Только если роль `localoca_app` ещё не создана | **Не повторять** |
| [security/06_update_runtime_permissions.sql](security/06_update_runtime_permissions.sql) | Если роль уже существует и нужно обновить права для `users.display_name`, личных точек и identity-последовательностей; выполнять после миграции 04 | Рассчитан на повторное применение |
| [migrations/07_migrate_photo_storage.sql](migrations/07_migrate_photo_storage.sql) | Перед развёртыванием API, которому требуется хранение фотографий в PostgreSQL | Рассчитан на повторное применение в рамках описанной схемы |
| [migrations/08_server_sessions.sql](migrations/08_server_sessions.sql) | Обязательно для API с серверным управлением сессиями; создаёт таблицу user_sessions | Рассчитан на повторное применение |

Для старой базы, в которой нет wishlist и личных точек, общий порядок — `03` → `04` → при необходимости `05` (если роли ещё нет) → `06` → `07` → `08`. После миграции `08` повторно выполни `06_update_runtime_permissions.sql`, чтобы выдать уже существующей роли права на `user_sessions`. Если часть объектов или роль уже существуют, пропускай соответствующий шаг после проверки фактического состояния базы.

Миграция `07` добавляет или проверяет `image_data` и `content_type`, ограничения размера и типа изображений и необходимые разрешения runtime-роли. Для старой базы её необходимо применить **до** развёртывания версии API, которая ожидает хранение фотографий в PostgreSQL.

Наличие файла миграции в репозитории не доказывает, что она выполнена в конкретной базе. Проверяй фактическую схему и права в Supabase.

## Runtime-роль и секреты подключения

API не должно подключаться как владелец базы или административная роль `postgres`. Используй отдельную роль `localoca_app` с минимально необходимыми разрешениями.

- Пароль, указанный в `05_create_app_role.sql`, должен быть уникальным и не совпадать с паролем владельца проекта.
- Строка подключения развёрнутого API хранится в Render как секрет `LOCA_DB_CONNECTION`.
- Секрет подписи сессий хранится в Render как `LOCA_SESSION_SECRET`.
- Для локальной разработки может использоваться `%LOCALAPPDATA%\LocaLoca\server-config.json`; пароль в актуальном формате защищён Windows DPAPI с областью `CurrentUser`.

Не коммить реальные значения этих параметров. Если секрет попал в историю Git, считай его раскрытым и замени, даже если последняя версия файла уже очищена.

Проверка API `/ready` подтверждает доступность базы, наличие нужных объектов схемы и runtime-разрешений. Она не запускает SQL-миграции и не исправляет конфигурацию автоматически.

## Проверка доступа через Supabase Data API

Для диагностики прямого доступа к таблицам через Supabase Data API используй [audits/check_supabase_data_api_access.sql](audits/check_supabase_data_api_access.sql).

Запрос показывает:

- состояние Row Level Security (RLS);
- прямые права ролей `anon`, `authenticated` и `PUBLIC` на таблицы и представления;
- права `EXECUTE` на функции и процедуры;
- политики RLS;
- default privileges для будущих объектов.

Это **только диагностический запрос**: он не изменяет таблицы, права или политики. Запускай его в Supabase SQL Editor под ролью с достаточными правами для просмотра сведений.

При анализе результата:
- если RLS выключен и публичные роли имеют доступ к пользовательским таблицам, проверь возможность чтения или изменения данных;
- если RLS включён, изучи каждую политику и разрешённые ею операции;
- проверь default privileges: новые объекты могут автоматически получать права;
- не выполняй массовые `REVOKE` или `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` без анализа последствий.

Сервер Loca Loca подключается к PostgreSQL через Npgsql под ролью `localoca_app`. Изменения прав для Supabase Data API не должны случайно лишить сервер нужных разрешений.

## Экспорт справочного каталога

Скрипт [tools/Export-AttractionsSeed.ps1](../tools/Export-AttractionsSeed.ps1) экспортирует справочник достопримечательностей из доступной разработчику базы в `seed/02_seed.sql`.

Скрипт использует `LOCA_DB_CONNECTION` или локальный файл `%LOCALAPPDATA%\LocaLoca\server-config.json`; поддерживаются старый формат и новый DPAPI-формат. Расшифровать DPAPI-пароль может только та же учётная запись Windows, которая создала конфигурацию. На компьютере должны быть установлены PostgreSQL Command Line Tools, включая `psql`.
