# Как внести вклад в Loca Loca

Спасибо за интерес к проекту. Можно предложить исправление, новую функцию, улучшение документации или сообщить об ошибке. Это руководство описывает безопасный процесс работы и требования к Pull Request.

## С чего начать

Перед началом проверьте [открытые Issues](https://github.com/teofobiaa/LocaLoca/issues) и Pull Request: возможно, задача уже обсуждается или выполняется.

- **Нашли ошибку или хотите предложить улучшение:** создайте [Issue](https://github.com/teofobiaa/LocaLoca/issues). Опишите контекст, фактическое поведение и ожидаемый результат.
- **Нужно сначала обсудить идею:** используйте [Discussions](https://github.com/teofobiaa/LocaLoca/discussions).
- **Хотите взяться за существующую задачу:** оставьте комментарий в Issue, чтобы не дублировать чужую работу.
- **Обнаружили уязвимость:** не публикуйте её в Issue, Discussions или Pull Request. Следуйте [SECURITY.md](SECURITY.md) и используйте приватный канал сообщения.

## Рабочая ветка

Не отправляйте изменения непосредственно в `main`. Для каждой самостоятельной задачи создавайте отдельную ветку от актуального `main`. Одна ветка должна содержать одно логически связанное изменение.

Рекомендуемые префиксы имён веток:

- `feat/` — новая функция;
- `fix/` — исправление ошибки;
- `docs/` — документация;
- `test/` — тесты и тестовая инфраструктура;
- `refactor/` — рефакторинг без изменения внешнего поведения.

Небольшой Pull Request с понятной областью изменений проще проверить и безопаснее объединить, чем несколько несвязанных задач в одном запросе.

### Fork и локальная копия

Если у вас нет прав записи в репозиторий, сначала создайте fork, затем клонируйте его и добавьте основной репозиторий как remote:

~~~powershell
git clone https://github.com/<ваш-ник>/LocaLoca.git
cd LocaLoca
git remote add upstream https://github.com/teofobiaa/LocaLoca.git
git fetch upstream
git switch -c fix/short-description upstream/main
~~~

Если у вас есть права записи в основной репозиторий, можно клонировать его напрямую и создать ветку от `origin/main`:

~~~powershell
git clone https://github.com/teofobiaa/LocaLoca.git
cd LocaLoca
git switch -c fix/short-description origin/main
~~~

Перед открытием Pull Request синхронизируйте рабочую ветку с последним `main`. Для fork используйте `upstream/main`, для прямого клона — `origin/main`. Если при синхронизации возник конфликт, разрешите его в своей рабочей ветке, проверьте итоговый diff и повторно запустите затронутые проверки. Не удаляйте и не перезаписывайте чужие коммиты.

## Требования к Pull Request

Открывайте Pull Request в `main`. В описании укажите:

1. **Что изменено и зачем.** Кратко опишите проблему и выбранное решение.
2. **Область влияния.** Перечислите затронутые компоненты, API-маршруты, таблицы, настройки или пользовательские сценарии.
3. **Связанные задачи.** Добавьте ссылку на Issue, если он есть.
4. **Проверки.** Приведите точные команды, которые запускали, и их результат. Не отмечайте проверку как успешную, если она не запускалась.
5. **Особые действия.** Отдельно укажите необходимость миграции БД, изменения конфигурации, ручной проверки или дополнительных шагов развёртывания.

Перед отправкой проверьте, что в diff нет временных файлов, случайных изменений форматирования, секретов и данных, не относящихся к задаче. Если изменение затрагивает поведение приложения, добавьте или обновите соответствующие автоматизированные тесты.

Проверяйте результаты всех обязательных CI-проверок, отображаемых в Pull Request. Если проверка упала, приложите ссылку на job и опишите причину; не скрывайте неуспешные или пропущенные проверки.

## Настройка разработки

Основная среда разработки клиента:

- Windows 10 версии 22H2 или Windows 11 x64;
- .NET SDK 10.0.100 или более поздняя версия в поддерживаемой ветке обновлений; точная версия проекта задаётся в корневом `global.json`;
- Visual Studio с компонентами WinUI 3, Windows App SDK и Windows SDK;
- Microsoft Edge WebView2 Runtime;
- доступ к NuGet для восстановления пакетов.

Клонируйте репозиторий, установите зависимости клиента и настройте облачный адрес API:

~~~powershell
git clone https://github.com/teofobiaa/LocaLoca.git
cd LocaLoca
.\tools\Install-CloudDependencies.ps1
~~~

Откройте `LocaLoca.sln`, дождитесь восстановления пакетов, выберите `Debug / x64 / Unpackaged` и запустите приложение клавишей F5.

Подробности настройки и конфигурации приведены в [README.md](README.md#для-разработчика).

## Тесты и проверки

Тесты находятся в отдельном решении `Tests/LocaLoca.Tests.sln`. Полный набор запускается из корня репозитория:

~~~powershell
dotnet test Tests/LocaLoca.Tests.sln --configuration Release
~~~

Для API- и Database-тестов требуется Docker Desktop с работающим Linux-контейнерным движком. Эти тесты используют одноразовые PostgreSQL 16-контейнеры и синтетические данные. Unit-тесты не требуют Docker или внешней базы.

При необходимости можно запускать уровни отдельно:

~~~powershell
# Unit — без Docker
dotnet test Tests/LocaLoca.Tests/LocaLoca.Tests.csproj --configuration Release

# API integration — требуется Docker
dotnet test Tests/LocaLoca.Api.Tests/LocaLoca.Api.Tests.csproj --configuration Release

# Database integration — требуется Docker
dotnet test Tests/LocaLoca.Database.Tests/LocaLoca.Database.Tests.csproj --configuration Release
~~~

Для изменений WinUI-клиента выполните Windows-сборку:

~~~powershell
.\tools\Build-Windows.ps1
~~~

Если изменён установщик, дополнительно соберите его:

~~~powershell
.\tools\Build-Installer.ps1
~~~

Автоматизированные тесты не заменяют ручную проверку пользовательского сценария, если затронуты WinUI, WebView2, установка или удаление приложения. Для документационных изменений проверьте ссылки, команды и соответствие текста фактическому поведению проекта; не указывайте выполнение программных тестов, если они не запускались.

Подробнее об уровнях тестирования и границах тестовой среды: [Tests/README.md](Tests/README.md).

## Изменения базы данных

Перед изменением SQL ознакомьтесь с [database/README.md](database/README.md).

- Не редактируйте опубликованные структурные миграции задним числом. Для нового изменения используйте следующий свободный номер миграции.
- Если меняется SQL-файл, контрольная сумма которого записана в `database/migrations/manifest.json`, обновите соответствующее значение SHA-256 и не меняйте контрольные суммы других файлов.
- Обновляйте тесты схемы и миграций вместе с SQL-изменениями.
- Проверяйте SQL в тестовом контуре на одноразовой базе. Не запускайте тесты или экспериментальные миграции против production Supabase.
- Не меняйте права runtime-роли шире, чем требуется конкретному сценарию. Объясните необходимость каждого нового разрешения в Pull Request.

Полный снимок схемы, seed-данные, миграции и скрипты безопасности имеют разные назначения. Не запускайте полный снимок схемы или seed поверх существующей рабочей базы.

## Безопасность и данные

Запрещено добавлять в Git или прикладывать к Issue/Pull Request:

- пароли, токены, ключи подписи, строки подключения и другие секреты;
- реальные персональные данные пользователей;
- production-дампы базы и конфигурационные файлы с секретами;
- логи, содержащие действующие учётные данные или пользовательские данные.

Для тестов используйте синтетические данные и временную инфраструктуру. Не подключайте тестовый процесс к рабочей Supabase-базе или production-секретам Render.

Если секрет попал в коммит, считайте его раскрытым: удаление из последней версии файла не отменяет утечку из истории Git. Такой секрет необходимо отозвать или заменить.
